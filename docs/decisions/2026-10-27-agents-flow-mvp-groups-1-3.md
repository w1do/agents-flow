## Решение и варианты

Решения, принятые внутри этапа:

1. **Одиннадцать таблиц в одной начальной миграции.** Вариант с миграцией
   на модель отклонён: схема менялась бы вслепую, пока нет живого прогона
   на PostgreSQL. Одна миграция `0001_initial_schema` — проще откатить.
2. **Rate limiter в памяти процесса** (`api/rate_limit.py`). Варианты —
   Redis или отдельная таблица — отклонены для MVP: лишняя зависимость
   на этом этапе. Цена: состояние теряется при рестарте, у нескольких
   воркеров счётчики независимы.
3. **Bootstrap администратора через advisory lock на PostgreSQL
   и `BEGIN IMMEDIATE` на SQLite.** Так гонка при старте двух процессов
   не создаёт двух админов.
4. **`git_remote` валидируется строго.** Запрещены remote-helper синтаксис,
   credentials в URL, query/fragment, управляющие символы; разрешены
   схемы https, ssh, git и SCP-форма. Причина — значение уходит в harness.
5. **`/harness/init` не назначает skills.** Новый агент стартует с пустым
   набором `skills: []`, набор выдаёт администратор. Это отход от первой
   реализации Sol; сознательно, чтобы не выдавать права по умолчанию.

## Критические моменты

**1. Финальной приёмки `final-gate-opus` не было.** Среда заблокировала
вызов как «самоодобрение». По правилам проекта без `FINAL: APPROVED`
в `main` не сливают; слияние сделано по прямому указанию пользователя.
Риск: независимой приёмки моделью другого семейства не выполнено.

**2. `Idempotency-Key` не реализован.** Заголовок описан в `docs/api.md`,
но игнорируется: повторный POST создаёт вторую сущность. Место —
задача 5.7. До тех пор документ обещает больше, чем код делает.

**3. `/harness/init` не назначает skills.** Агент получает `skills: []`;
набор выдаёт администратор (задача 4.2).

**4. Rate limiter живёт в памяти процесса.** Не общий между воркерами,
сбрасывается при рестарте. Для MVP допустимо, для нескольких процессов
нужен общий стор.

**5. Bootstrap администратора проверен только на SQLite.** Ветка
advisory lock для PostgreSQL написана, но живого конкурентного прогона
на PostgreSQL не было.

**6. `git_remote` валидируется строго** — см. решение 4. Расширение
списка схем требует правки валидатора.

**7. Alembic на реальном PostgreSQL не прогонялся.** Docker в sandbox
закрыт, проверка шла на SQLite. `--sql` даёт корректный DDL для
PostgreSQL, но живой прогон нужен.

**8. Часть проверок terra не выполнила.** Оба прогона: не было `python`,
закрыт Docker, запрещён `rm -f`. Alembic и поиск секретов продублировал
оркестратор вручную.

**9. Спеки закрыты частично.** Требования по claim/result, busy/online
и Telegram относятся к группам 5–7.

**10. `TRUSTED_PROXY_IPS` валидируется, но не применяется.** uvicorn
нужно запускать без `--proxy-headers` либо с `--forwarded-allow-ips`,
иначе реальный адрес клиента в rate limiter и логах будет адресом прокси.
