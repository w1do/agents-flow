Изменения относительно версии 4: вход и управление переехали в Telegram. Голос диктуется в бот, выбор проекта делается кнопкой. Статусы задач приходят в один сообщение, которое обновляется по этапам. MCP называется `agents-flow`.

## 1. Цель [MVP]

Голосовой харнесс в Telegram. Диктуешь задачу боту, выбираешь проект кнопкой, задача уходит в песочницу. Агент работает, отчитывается через MCP `agents-flow`, а ты видишь статус по этапам в том же чате.

Ничего не устанавливается на машине пользователя. Управление: Telegram и консоль.

MVP: голос в Telegram → выбор проекта → песочница → агент → MR → статус в Telegram.

## 2. Принципы [MVP]

1. **Вход в Telegram.** Голос, текст и кнопки в одном чате. Отдельного приложения и Shortcuts нет.
2. **Человек выбирает проект.** Polza AI предлагает варианты, решение за пользователем.
3. **Исполнение только в песочницах.** Задачи не выполняются на машине пользователя и на сервере.
4. **Нет клиента.** Сервер управляет песочницей через Novita API. Бинарника и пакета в песочнице нет.
5. **MCP — единственный интерфейс управления.** Всё, что можно сделать, есть как инструмент MCP `agents-flow`: задачи, процессы, чекпоинты, песочницы, спецификация, настройки. Консоль, Telegram, голос и внешние MCP-клиенты (включая Claude) вызывают одни и те же инструменты. Прямой записи в таблицы в обход MCP нет.
6. **Универсальность.** Ядро не содержит доменной логики. Новая возможность добавляется skill-файлом.
7. **Состояние в Postgres.** Проекты, задачи, чекпоинты, настройки, skills, интеграции, профили.
8. **Гейты проверяет харнесс.** Коммит, пуш, тесты, деплой, MR проверяются механически.
9. **Секреты не в коде и не в файлах.** Подставляются в песочницу при активации и стираются при очистке.
10. **Один язык.** Сервер на Python, модели Pydantic общие с консолью через `shared/`.

## 3. Компоненты [MVP частично] (консоль — позже)

| Компонент | Технология | Назначение |

## 4. Модель данных [MVP частично]

MVP: Task, TaskEvent, Routing, SpecItem, Sandbox, Checkpoint (минимум). Позже: Preference/Memory, Integration, MCPServer, SandboxProfile с версиями, Skill, Process.

- **TelegramChat.** chat_id, пользователь, активный диалог.
- **Agent.** Тип (claude-code, codex, кастомный), роль, команда запуска, параметры бюджета.
- **Workspace.** Репозиторий, тип агента, инструкция, спецификация, skills, интеграции, гейты, голосовые названия.
- **Task.** id, kind (`plan`, `implement`, `check`), workspace, текст, агент, песочница, статус (`new`, `choosing`, `active`, `testing`, `ready`, `merged`, `planning`, `backlog`, `error`, `stalled`, `paused`, `trash`), результат, timestamps.
- **TaskEvent.** task, статус, текст, момент. Лента для Telegram и журнала.
- **Process.** id, задача, песочница, название, состояние (`running`, `done`, `failed`), время начала и окончания. Список процессов для консоли и команд.
- **Канбан.** Не отдельная таблица: это представление `Task` по колонкам статусов.
- **Routing.** Варианты, которые предложила Polza, выбор пользователя, сырой ответ модели.
- **Checkpoint.** task, summary, изменённые файлы, полный diff текстом, следующий шаг, статус, токены за сессию.
- **SpecItem.** Пункт спецификации: id, текст, статус, ссылка на последний чекпоинт. В таблице задач источник `spec`.
- **Skill.** Имя, описание, MD-инструкция. Общая библиотека.
- **Integration.** Имя, API URL, `key_ref`, инструкция для агента, actions.
- **MCPServer.** Имя, ключ → значение (секреты как ссылки), привязка к профилю.
- **Sandbox.** id, тип агента, статус (`paused`, `active`, `error`), текущая задача, версия профиля.
- **SandboxProfile.** Версионируемый набор: предпочтения, память, конфиги агентов, MCP, skills, репозитории, версия bootstrap-скрипта.
- **Preference / Memory.** Общие предпочтения и память. Из них генерируются `CLAUDE.md` и `AGENTS.md`.

## 5. Голосовой путь через Telegram [MVP частично]

MVP: шаги 1–4 для класса «работа». Позже: полный выбор проекта с «Другой проект», уведомления о неуверенности.

1. Диктуешь голосовое сообщение боту (или пишешь текст). Сервер получает его через webhook и переводит в текст.
2. Задача создаётся в статусе `choosing`. Polza AI предлагает до трёх workspace, самый вероятный отмечен первым.
3. Бот присылает кнопки: название проекта для каждого варианта и кнопка «Другой проект», которая показывает полный список.
4. Выбираешь кнопку. Дальше путь зависит от класса команды (раздел 5.0): для работы создаётся задача `plan`, а не сразу реализация.
5. Агент работает в песочнице и отчитывается через `agents-flow`. Сервер пишет события в `TaskEvent` и обновляет сообщение в Telegram.
6. Гейты и очистка выполняются сервером через exec-команды, после них песочница уходит на паузу.

Сообщение о задаче одно. Этапы дописываются в него, а не присылаются отдельными сообщениями.

## 5.0. Классы голосовых команд [MVP частично]

MVP: классы «работа» и «запрос состояния». Позже: «проверка» (задача `check`) и класс «управление» в полном виде.

Polza определяет класс команды до любых действий. Класс задаёт путь. Голос никогда не запускает разработку напрямую.

**1. Работа** («создай», «сделай», «добавь», «исправь», «доделай», «поправь»). Всегда начинается со спецификации, даже для мелкой правки:
- Создаётся задача `plan`. Песочница активируется с планировщиком: Claude Code с инструкцией OpenSpec.
- Планировщик пишет спецификацию в репозитории (proposal, design, список задач) и декомпозирует работу на пункты.
- Через MCP он синхронизирует спецификацию (`sync_spec`) и создаёт задачи реализации (`create_task`, `kind=implement`, статус `backlog`) в канбане.
- Задача `plan` завершается. В Telegram приходит итог: «спецификация готова, задач: N» со списком.
- Реализацию делают агенты по канбану. Диспетчер берёт задачи из `backlog` по приоритету.

**2. Проверка** («проверь», «посмотри, работает ли»). Если нужно только прочитать состояние, это класс 3. Если нужно запустить код (тесты, сборка), создаётся задача `check`: только чтение, без коммитов и мерджа, результат уходит в Telegram. Если проверка приводит к исправлению, это уже класс 1.

**3. Запрос состояния** («что по проекту», «статус», «что делает агент»). Ответ — отчёт в Telegram, собранный из MCP-чтения. Песочницы не запускаются.

**4. Управление** («пауза», «возобнови», «останови»). Операторские инструменты MCP, раздел 5.1.

Если Polza не уверена между классами 1 и 2, она спрашивает кнопкой. Класс 1 при сомнении не запускается.

## 5.1. Голосовые команды управления [позже]

MVP: только пауза и возобновление одной песочницы. Остальное позже.

Команды управления тоже проходят через Polza. Но Polza возвращает не выбор проекта, а намерение: действие из закрытого списка, цель и фильтр. Например, «поставь все песочницы на паузу срочно» → `pause_sandboxes`, цель: все.

Закрытый список действий:
- `pause_sandboxes` — все или выбранные песочницы;
- `resume_sandboxes` — возобновить песочницы;
- `pause_tasks` — все активные или выбранные задачи;
- `resume_tasks` — продолжить приостановленные задачи;
- `stop_task` — остановить задачу;
- `status` — ответить на вопрос о состоянии.

Порядок обработки:
1. Polza возвращает действие, цель и уверенность. Всё, что не входит в список, отклоняется с ответом «не понял, вот что умею».
2. Сервер проверяет chat_id владельца, что цели существуют и что действие применимо (нельзя возобновить задачу, которая не на паузе).
3. Если цель неоднозначна («поставь задачи на паузу» при трёх активных), бот показывает кнопки с задачами и ждёт выбора.
4. Исполнение через MCP `agents-flow`. Модель сама ничего не исполняет.

Подтверждение:
- Пауза выполняется сразу, без подтверждения. Ответ приходит с итогом: сколько песочниц и задач остановлено и что сохранено.
- Возобновление и остановка требуют кнопку «Подтвердить». Возобновление запускает расход, остановка необратима.

Что значит пауза:
- **Задача.** Агент останавливается, сохраняется чекпоинт, креды стираются, статус `paused`. Worktree и ветка `task/<id>` остаются.
- **Песочница.** Сначала все агенты останавливаются и сохраняют чекпоинты, креды стираются, затем вызывается пауза Novita. Worktree остаётся, потому что незакоммиченная работа не должна пропасть. Это отступает от правила «очистка перед паузой», см. вопрос 11.
- **Возобновление задачи.** Песочница возобновляется, выполняется `git fetch`, креды выдаются заново, агент продолжает с последнего чекпоинта.

Каждая команда пишет событие через `agents-flow`, поэтому канбан и журнал остаются полными.

## 6. Статусы и сообщения в Telegram [MVP частично]

MVP: два этапа «начата» и «готова, MR создан», одно сообщение с дописыванием. Позже: «тестирование», «влита MR», отдельные сообщения об ошибках, кнопки «Остановить» и «Повторить», команды статуса.

Этапы (обязательные):

```
Задача [авторизация] (начата)
Задача [авторизация] (тестирование)
Задача [авторизация] (готова)
Задача [авторизация] (влита MR)
```

Откуда берётся каждый этап:
- **начата.** Песочница активирована, агент запущен, первое событие от `agents-flow`.
- **тестирование.** Агент сообщил о завершении работы, сервер запускает тесты.
- **готова.** Тесты зелёные, коммит запушен, MR создан.
- **влита MR.** Авто-мердж прошёл.

Для задачи `plan` этапы другие: «планирование» → «спецификация готова» с числом задач в канбане. Задачи реализации получают свои сообщения по тем же этапам, что выше, когда их берёт агент.

Отдельные сообщения при отклонениях:
- сорвана (связь с песочницей не восстановилась, задача уходит на другую песочницу с последнего чекпоинта);
- ошибка гейта (с причиной и кнопкой «повторить»);
- превышен бюджет;
- нет уверенности в выборе проекта (до выбора кнопкой, если пользователь не ответил).

Кнопки в сообщении задачи: «Остановить», «Показать чекпоинт», «Повторить» при ошибке.

Команды статуса: «что делает агент», «какие задачи открыты», «сколько потрачено» пишутся в бот текстом или голосом. Ответ берётся из `agents-flow` и той же таблицы событий.

## 7. Сервер (FastAPI) [MVP частично]

MVP: `POST /tasks`, webhook Telegram, очередь без `SKIP LOCKED`-гонок (одна песочница), приём отчётов `report_task`, MCP. Позже: продление сессии, heartbeat, перенос сорванных задач, полный диспетчер.

Эндпоинты:
- `POST /telegram/webhook` — входящие сообщения и нажатия кнопок. Проверка секрета webhook.
- `GET /tasks/{id}` — статус и результат, нужен консоли.
- `GET /bootstrap/{profile_id}.sh` — bootstrap-скрипт по одноразовому токену.
- MCP `agents-flow` (раздел 11), подпись токеном задачи.

Диспетчер:
- Выбирает задачу `new` через `FOR UPDATE SKIP LOCKED`.
- После выбора проекта активирует песочницу, запускает агента exec-командой.
- Продлевает сессию песочницы на время активной задачи.
- Если exec или песочница не отвечают, повторяет попытки каждые 10 минут. Статус пишется файлом в песочнице, поэтому после восстановления связи сервер понимает, на чём остановился агент. Если связь не восстановилась, задача помечается `stalled` и уходит на другую песочницу с последнего чекпоинта.
- Ставит песочницу на паузу только после того, как команда очистки вернула успех.

Требования: асинхронный сервер; доступ к БД только через SQLAlchemy ORM (async); входные данные валидируются Pydantic; миграции через Alembic.

ENV:
- `DATABASE_URL`
- `ADMIN_EMAIL`, `ADMIN_PASSWORD` (первый старт, далее сверка по хешу в БД)
- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (владелец), `TELEGRAM_WEBHOOK_SECRET`
- `POLZA_AI_URL`, `POLZA_AI_KEY`, `POLZA_AI_MODEL`
- `STT_PROVIDER`, `STT_API_KEY` (открыто)
- `NOVITA_API_KEY`, `NOVITA_DOMAIN`

Бот принимает команды только от `TELEGRAM_CHAT_ID`. Остальные сообщения отбрасываются.

## 8. Консоль [позже]

MVP: настройки в конфигурационном файле, канбан смотрим через Telegram (`list_tasks`).

- **Агенты.** Роли и параметры бюджета для Claude Code, Codex, кастомных агентов.
- **Workspace.** Репозиторий, тип агента, инструкция, спецификация, skills, интеграции, гейты, голосовые названия.
- **Skills.** Библиотека MD-файлов: создание, загрузка, редактирование, привязка к workspace.
- **Интеграции.** Имя, API URL, ключ по ссылке на секрет, инструкция, actions.
- **Мои MCP.** Ключ → значение.
- **Песочницы.** Создание по кнопке, статус каждой, версия профиля, журнал активаций.
- **Профиль песочницы.** Предпочтения, память, конфиги агентов, MCP, skills, репозитории, ссылка на bootstrap-скрипт.
- **Наблюдаемость (только чтение).** Канбан, задачи, процессы, события, чекпоинты, решения Polza, расход токенов. Консоль вызывает те же инструменты MCP, что и любой клиент. Прямых правок в обход MCP нет. Создание песочниц и настройки остаются в консоли: это не состояние задач.

Вход: один admin-аккаунт. Смена пароля при утере: команда на сервере, например `docker exec <container> harness-server reset-password --email <email> --password <new>`.

## 9. Песочницы (Novita AI) [MVP частично]

MVP: одна песочница, созданная вручную, пауза и возобновление одной командой. Позже: пул, создание по кнопке, продление таймаута, учёт стоимости простоя, привязка по типу агента.

**Модель.** Общий пул, не привязан к проекту. Диспетчер выбирает свободную песочницу нужного типа агента. Одна песочница — одна задача одновременно.

*Открытый вопрос: привязка через тип агента (рекомендуется) или через конкретную песочницу.*

**Создание одной командой.** В консоли указывается ссылка на bash-скрипт. Песочница скачивает и запускает его. Скрипт генерируется сервером из профиля и ставит:
1. `claude` (Claude Code), `codex`, `nano`.
2. Клонирует выбранные репозитории.
3. Раскладывает skills для Claude и Codex.
4. Записывает MCP-серверы в конфиги агентов, включая `agents-flow` с адресом сервера.
5. Создаёт `CLAUDE.md` и `AGENTS.md` из предпочтений и памяти.

Свойства скрипта:
- Секретов в нём нет. Ключи MCP и git-токены приходят от сервера по одноразовому токену песочницы.
- Идемпотентен: при каждой активации повторно запускается, установленное не переустанавливается, skills и MCP обновляются.

*Открытый вопрос: клонировать все репозитории при создании или при первой задаче.*

**Жизненный цикл:**
- `paused` — простой в пуле, состояние сохранено.
- `active` — назначена задача. Сервер выдаёт креды на одну задачу, в песочнице выполняется `git fetch`.
- Агент работает в worktree от свежего `origin/main` на ветке `task/<task_id>`.
- После гейтов worktree, локальная ветка и креды удаляются. Успех очистки разрешает паузу.

**Таймаут.** У Novita по умолчанию песочница завершается через заданное время, состояние теряется. Сервер продлевает сессию на время активной задачи.

**Стоимость.** Посекундная оплата ресурсов. Уточнить, списывается ли что-то за паузу.

## 10. Выполнение задачи в песочнице [MVP частично]

MVP: запуск агента через exec, коммит, пуш, MR, фильтр секретов перед коммитом. Позже: полные гейты (тесты как отдельный шаг, деплой), очистка с удалением кредов, `harness-snap`.

Отдельного бинарника или пакета в песочнице нет. Сервер управляет ею через Novita API: exec-команды, запись файлов, чтение статуса, пауза.

Последовательность на одну задачу:
1. **Запуск агента.** Сервер exec-командой запускает `claude` или `codex` в worktree с текстом задачи. Агент сам выбирает skills по описанию.
2. **Отчёты.** Агент через `agents-flow` сообщает этапы, чекпоинты, статус. Параллельно пишет файл статуса в песочнице. Сервер читает его exec-командой после обрыва связи.
3. **Бюджет.** Claude Code в режиме JSON отдаёт usage после завершения, поэтому точный учёт возможен по итогам сессии. Остановка в процессе не решена (раздел 17).
4. **Гейты.** Сервер exec-командами выполняет: проверку коммита, пуш, тесты, деплой, MR, авто-мердж после зелёных тестов. Гейты не через skills.
5. **Чекпоинт.** Через `agents-flow` (`save_checkpoint`). Если его нет, сервер берёт diff и список файлов exec-командой.
6. **Очистка.** Exec-командой удаляются worktree, локальная ветка, креды. Успех очистки разрешает паузу.

Креды приходят на активацию и стираются при очистке. Долгоживущих секретов в песочнице нет.

## 10.1. Спецификация, чекпоинты и передача работы [MVP частично]

MVP: OpenSpec-спецификация планировщиком, `sync_spec`, задачи в `backlog`. Позже: снимки раз в минуту, чекпоинты, сессии и handoff, пороги контекста.

**Спецификация (OpenSpec).** Агент пишет спецификацию в репозитории. Через `sync_spec` пункты синхронизируются в таблицу `SpecItem`, и каждый пункт может стать задачей с источником `spec`. Источник правды — файл в репозитории, `SpecItem` — зеркало. При расхождении побеждает репозиторий, расхождение пишется в журнал.

**Старт сессии.** Агент читает спецификацию и статусы пунктов, пункты `completed` не трогает, для незавершённого читает handoff и продолжает с места остановки.

Три уровня фиксации:
- **Снимок (раз в минуту).** Сервер через exec запускает скрипт `harness-snap`, который ставится bootstrap-скриптом. Скрипт проверяет worktree, прогоняет фильтр секретов, делает WIP-коммит в `task/<id>` и пушит. В БД пишется запись: хеш коммита, число файлов, время. Diff в БД не хранится, он в git.
- **Чекпоинт сессии.** Агент по запросу пишет summary и следующий шаг через `save_checkpoint`. Это семантическая часть, и снимок от неё не зависит.
- **Handoff.** Запись при смене сессии. Описан ниже.

Снимок делает сервер, а не агент. Если агент завис, его снимков не будет, а exec видит состояние независимо от агента.

**Контекст и пороги.**
- Считается контекст последнего ответа: input + cache read + cache creation. Суммарный расход за сессию не используется.
- Целевой порог 120k: сессия заканчивается на ближайшей границе отрезка.
- Предел 150k: максимально допустимый контекст сессии. Выше него сессия останавливается немедленно, handoff строится без summary агента.

**Как устроен запуск.**
- Агент работает отрезками: `claude -p` с ограничением числа ходов, вывод пишется в файл потока `stream-json` в песочнице.
- Между отрезками сервер через exec читает usage из файла и решает, что делать. Граница отрезка — безопасная точка: агента не прерывают на полуслове.
- Продолжение в той же сессии: `--resume` с id сессии. Новая сессия: без `--resume`, с контекстом из handoff.

**Триггеры смены сессии** (любой из):
1. Контекст ≥ 120k на границе отрезка.
2. Жёсткий порог 150k.
3. Отрезок завершился с ошибкой или без признака завершения.
4. Пропал heartbeat: новая песочница.
5. Вручную: `force_handoff(task_id)`.

**Как понять, что сессия закончилась.** Процесс отрезка завершился (код выхода известен), и handoff записан, либо прошло 3 минуты без него. В последнем случае сервер строит handoff сам. Новая сессия стартует только когда старый процесс завершён (проверка через exec) и handoff записан. Две сессии одной задачи одновременно не работают.

**Состав handoff.**
- Детерминированная часть, из git: список изменённых файлов, последний изменённый файл по времени правки, хеш последнего коммита, статистика diff.
- Семантическая часть, от агента, если он успел: summary, следующий шаг, открытые вопросы.

Если агент не успел написать summary, следующая сессия работает на детерминированной части и спецификации. Работа не теряется.

**Состояния сессии:** `running` → `handoff_pending` → `closed` (причина: `threshold`, `completed`, `error`, `sandbox_lost`, `manual`) → новая `running`. Задача остаётся `active`, пока сессии идут. Сообщение `completed` от агента только запускает гейты.

**Потеря песочницы.** Теряется не больше минуты работы. Новая песочница: clone или fetch, checkout `task/<id>`, handoff последней сессии.

**Инструменты.** Агент: `save_checkpoint`, `save_handoff`, `heartbeat`. Оператор: `list_sessions`, `force_handoff`.

**Что меняется относительно прежних решений.** Полный diff переезжает из БД в git. В БД остаются хеш, summary и метаданные. Это сокращает рост базы (C7).

**Исключение из правила «без раннера».** Один shell-скрипт `harness-snap`, установленный bootstrap-скриптом и вызываемый через exec. Это не процесс и не бинарник, но его нужно учитывать в ТЗ.

**Решено.** Порог считается по контексту сессии, а не по общему расходу. Целевой порог 120k, предел 150k.

**Проверено (документация Claude Code и разбор формата сторонним источником).**
- `--output-format stream-json` с `--verbose` (и опционально `--include-partial-messages`) выдаёт построчные JSON-события в реальном времени.
- В событиях `assistant` есть `message.usage` с полями `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`. Контекст последнего вызова = сумма input, cache read и cache creation.
- Последнее событие `result` содержит итоговый `usage` и `total_cost_usd`. Стоимость кумулятивна за сессию, в том числе при `--resume`.

**Что проверить на реальном запуске до старта:**
- Один ответ API может прийти несколькими событиями. Считать по `message.id`, без суммирования одинаковых usage.
- Официальная документация описывает usage в JSON-ответе, а покомпонентно в `stream-json` подтверждено только сторонним разбором. Нужен тестовый прогон, который сверит сумму с `result`.
- Флаг `--max-turns` для ограничения отрезка проверить в справке CLI: в документации headless он не описан.
- Рекомендуется `--bare`, чтобы отрезок не подхватывал чужие hooks и `CLAUDE.md` с хоста.

## 11. MCP `agents-flow` [MVP частично]

MVP: `create_task`, `sync_spec`, `report_task`, токен задачи. Позже: остальные инструменты из списков ниже, разделение `read`/`operate`/`admin`, отзыв токенов.

MCP-сервер на стороне харнесса и единый интерфейс управления. Консоль, Telegram, голос и внешние MCP-клиенты (включая Claude) вызывают одни и те же инструменты. Логика живёт в сервисном слое сервера, MCP и консоль его только вызывают.

Два вида доступа:
- **Токен задачи.** Выдаётся при активации песочницы. Агент видит только инструменты отчётов и только для своей задачи. Вызвать операторские инструменты он не может.
- **Операторский токен.** Выдаётся в консоли, имеет области `read`, `operate`, `admin`, может быть отозван. Telegram работает с ним, привязанным к chat_id владельца.

Опасные инструменты (`stop_task`, `delete_sandbox`, `resume_sandboxes` при выборе всех, `delete_skill`) требуют параметр `confirm=true`. Telegram передаёт его только после нажатия кнопки «Подтвердить».

Все вызовы пишутся в журнал с указанием источника: агент, консоль, Telegram, внешний клиент.

Инструменты агента (токен задачи, только свои задачи):
- `report_task(status, text)` — этап задачи (начата, тестирование, готова). Сервер пишет `TaskEvent` и обновляет Telegram.
- `save_checkpoint(summary, next_step, files, diff)` — чекпоинт.
- `report_process(name, state)` — старт и окончание процесса в песочнице (сборка, тесты, деплой).
- `stop_task(task_id)` — остановка по кнопке «Остановить» в Telegram или по команде голосом. Кнопка не пишет в таблицы сама, она вызывает этот инструмент.
- `pause_task(task_id)`, `resume_task(task_id)` — пауза и продолжение задачи (раздел 5.1).
- `pause_sandbox(sandbox_id)`, `resume_sandbox(sandbox_id)` — пауза и возобновление песочницы.
- `sync_spec(items)` — синхронизация спецификации OpenSpec с таблицей `SpecItem`. Пункты становятся задачами с источником `spec`.
- `list_tasks`, `task_history`, `agent_status`, `list_processes` — чтение состояния. Доступны и агенту, и голосовым командам в Telegram.
- `skills_manifest`, `get_skill`, `get_mcp_config` — синхронизация skills и MCP для workspace задачи. Агент видит только свой workspace.
- Планировщик (задача `plan`) дополнительно: `sync_spec`, `create_task` с `kind=implement` и статусом `backlog`, только в своём workspace. Реализация, мердж и смена статусов ему недоступны.

Агент не отправляет сообщения в Telegram сам. Это делает сервер по событиям, так что формат сообщений контролирует харнесс.

Операторские инструменты (операторский токен):
- **Задачи:** `create_task(text, workspace_id?)`, `get_task`, `choose_workspace(task_id, workspace_id)`, `pause_task`, `resume_task`, `stop_task` (confirm), `retry_task`, `set_task_priority`.
- **Песочницы:** `list_sandboxes`, `create_sandbox(agent_type)`, `pause_sandbox`, `resume_sandbox`, `pause_sandboxes(filter)`, `resume_sandboxes(filter, confirm)`, `delete_sandbox` (confirm).
- **Процессы и чекпоинты:** `list_processes`, `list_checkpoints`, `get_checkpoint`.
- **Спецификация:** `list_spec`, `sync_spec`.
- **Workspace и агенты:** `list_workspaces`, `get_workspace`, `update_workspace`, `list_agents`, `update_agent`.
- **Skills:** `list_skills`, `upsert_skill`, `attach_skill`, `delete_skill` (confirm).
- **Интеграции и MCP:** `list_integrations`, `upsert_integration`, `list_mcp`, `set_mcp_value`, `delete_mcp_value`. Секреты передаются только ссылками. Читающие инструменты значения секретов не возвращают.
- **Профиль песочницы:** `get_profile`, `update_profile` (создаёт новую версию), `get_bootstrap_link`.
- **Бюджет:** `usage(period)`.

Голосовая команда в Telegram — это не отдельный путь. Polza разбирает текст в одно из действий выше и вызывает соответствующий инструмент через MCP (раздел 5.1).

## 12. Skills, интеграции [позже]

MVP: skills кладутся в репозиторий вручную, интеграций нет.

**Skills и MCP синхронизируются через MCP.** Библиотека в Postgres — единственный источник правды. Файлы в песочнице — копия на момент активации и кэш.

- При старте задачи агент вызывает `skills_manifest`: список skills его workspace с именем, описанием, версией и хешем. Тело подгружается через `get_skill(name)`, если нужно.
- Если в манифесте версия новее локальной копии, агент берёт новую. Новый skill или правка доступны всем агентам без переустановки.
- `skills_manifest` вызывается и при каждом `report_task`, поэтому работающий агент получает обновление на следующем этапе.
- Список MCP и конфиг отдаёт `get_mcp_config`, секреты только ссылками. Конфиг перечитывается при старте задачи.
- Изменение skill в консоли создаёт новую версию. Telegram получает уведомление, какие workspace затронуты.
- Bootstrap раскладывает копии как запасной вариант, если MCP недоступен.

**Несколько workspace на одном харнессе.** Каждый workspace — набор: репозиторий, тип агента, skills, интеграции, гейты, голосовые названия. Примеры:
- **Разработка продукта.** Репозиторий приложения, Claude Code, skills для кода, гейты: тесты, деплой, MR, мердж.
- **Тексты и документы.** Репозиторий с текстами, Claude Code, skills для редактуры и стиля, гейты: коммит и пуш, без деплоя.
- **Третий проект.** Свой репозиторий, своя CRM-интеграция, свой набор гейтов.

Правило одно: любая задача выполняется в песочнице. Workspace меняет настройки, а не путь исполнения.

**Skill ↔ интеграция.** Skill не содержит ключей. Он ссылается на интеграцию по имени и объясняет, когда её вызывать.

**Интеграции (CRM и др.).** Настраиваются в консоли, передаются в песочницу при активации.

MVP: токен задачи для MCP, проверка chat_id, фильтр секретов, HTTPS. Позже: второй фактор для опасных команд, журнал вызовов с источником, отзыв токенов, остальные строки таблицы.

## 16.0. Сквозной срез (первый запуск) [MVP]

Цель: один раз пройти весь путь от голоса до MR с сообщением в Telegram. Скорость, удобство и полнота потом.

**Что обязательно входит:**
1. Telegram: текст и голос (STT), кнопка выбора проекта, один workspace.
2. Polza: определяет класс команды (раздел 5.0). Для среза достаточно классов «работа» и «запрос состояния».
3. Класс «работа»: задача `plan` → планировщик в песочнице пишет OpenSpec-спецификацию → `sync_spec` и `create_task` (`implement`, `backlog`).
4. Исполнитель: берёт одну задачу из `backlog` → Claude Code в ветке `task/<id>` → коммит → пуш → MR.
5. Telegram: два этапа, «начата» и «готова, MR создан». Мердж руками.
6. MCP `agents-flow`, минимум: `create_task`, `sync_spec`, `report_task`.
7. Одна песочница, созданная вручную через Novita, с минимальным bootstrap-скриптом: `claude`, `git`, клон репозитория, конфиг MCP. Пауза и возобновление через одну команду.
8. Минимум безопасности: фильтр секретов перед коммитом (A3), токен задачи для MCP (A2), проверка chat_id (C6 без второго фактора).

**Что сознательно не входит:**
- консоль (настройки в конфигурационном файле);
- канбан-экран (задачи смотрим через Telegram-команду `list_tasks`);
- синхронизация skills (кладём в репозиторий вручную);
- сессии, handoff и порог контекста (короткие задачи; если задача упёрлась в лимит, она падает с ошибкой, и это сигнал, а не баг);
- бюджет, `harness-snap` (коммит делается в конце задачи), heartbeat (проверяем вручную);
- параллельность, staging и main, автоматический мердж;
- утверждение спецификации (пункт 15).

**Что остаётся обязательным даже в срезе:** тесты — если команда тестов не задана, задача помечается «без тестов», а не «тесты зелёные». Это важно: без этого «готова» ничего не значит. Мердж руками остаётся страховкой.

**Критерий готовности:** голосом «создай X» → спецификация → задачи в `backlog` → агент делает одну задачу → MR создан → сообщение в Telegram. Если это работает, срез принят.

**Порядок работ:**
1. Проверка Novita: exec, пауза, возобновление.
2. Схема Postgres и минимальный сервер.
3. Telegram: голос, текст, кнопка проекта.
4. Polza: классификация двух классов.
5. Запуск агента через exec в песочнице.
6. MCP: три инструмента.
7. Планировщик с OpenSpec.
8. Исполнитель: коммит, пуш, MR.
9. Итог в Telegram.

**Решение, которое нужно принять до начала:** GitHub или GitLab. Без этого нельзя создать MR.

## 16.1. Риски и нюансы [MVP частично]

MVP: все пункты группы A (до первого запуска), B1 и B2 (тесты не зелёные по умолчанию, идемпотентные гейты). Позже: остальные пункты B, все пункты C.

Каждый пункт имеет меру, которую нужно сделать до или во время реализации. Уровни: **A** — до первого запуска, **B** — до авто-мерджа, **C** — устойчивость и эксплуатация.

### A. До первого запуска

- **A1. Novita не проверена.** Проверить по документации и на тестовой песочнице: exec-команды, запись файлов, пауза с сохранением, продление таймаута, стоимость пауз. Результат фиксируется в ТЗ.
- **A2. Доступ песочницы к серверу.** Публичный HTTPS-эндпоинт MCP, доступный из Novita. Токены задачи действуют только до завершения задачи. Проверить через Dokploy.
- **A3. Секреты в чекпоинтах и логах.** Фильтр до записи в БД: по шаблонам (ключи, токены) и по значениям кредов, выданных на задачу. Журнал и Telegram проходят тот же фильтр. Полный diff хранится с замазанными значениями.
- **A4. Дубли из Telegram.** Ключ идемпотентности по `update_id` и по `callback_query.id`. Повторное нажатие кнопки не создаёт новую активацию.
- **A5. Гонка за песочницу.** Блокировка на строку песочницы при выборе (`SKIP LOCKED` или аналог). Активация идемпотентна: повторный вызов для той же задачи возвращает текущее состояние.

### B. До авто-мерджа

- **B1. Нет тестов — нет зелёного.** Гейт «тесты» по умолчанию не пройден, если в workspace не заданы команды тестов. Зелёным он становится только по явной команде и её коду возврата.
- **B2. Гейты идемпотентны.** Каждый шаг (push, создание MR, мердж) проверяет, не выполнен ли он уже. Стоп или обрыв посреди гейтов продолжается с того же шага.
- **B3. Конфликты в одном репозитории.** Очередь на репозиторий: параллельно работает одна задача на репо, остальные ждут. Для разных веток в одном репо допускается параллельность при отсутствии пересечения файлов. Конфликт при rebase переводит задачу в `error` с причиной.
- **B4. Откат.** Каждый мердж в main регистрируется. Откат — отдельная команда (`revert_task`), которая создаёт revert-коммит и проходит те же гейты.
- **B5. Staging по умолчанию.** Пока не накоплена статистика успешных задач, мердж идёт в staging. Переход на main — отдельная настройка workspace с подтверждением.

### C. Устойчивость и эксплуатация

- **C1. Потеря песочницы.** Периодический WIP-пуш в `task/<id>` каждые N минут или при каждом чекпоинте. Незакоммиченное при паузе сохраняется как WIP-коммит (вопрос 11).
- **C2. Heartbeat.** Агент или обёртка отправляет `heartbeat` через MCP раз в минуту. Нет heartbeat за 5 минут — задача `stalled`, песочница проверяется, при необходимости возобновляется или заменяется.
- **C3. Лимиты задачи.** Максимум времени, шагов и токенов на задачу. Превышение останавливает задачу и отправляет причину. Это отдельно от бюджета на месяц.
- **C4. Polza недоступна.** Запасной путь: кнопки со всеми workspace без предложения. Задача не зависит от модели.
- **C5. Голосовой путь.** Конвертация OGG, таймаут распознавания, длинные сообщения, проверка распознавания названий проектов на реальных командах до запуска.
- **C6. Защита Telegram-аккаунта.** Опасные команды (`stop_task`, `resume_sandboxes`, `delete_sandbox`) требуют подтверждения кнопкой и паролем или кодом из отдельного приложения. Одного chat_id недостаточно.
- **C7. Хранение.** Политика: голосовые файлы не хранятся дольше суток, транскрипции и события — N месяцев, чекпоинты — до закрытия задачи плюс срок. Ежедневный бэкап Postgres и проверка восстановления.
- **C8. Версии CLI.** `claude` и `codex` закрепляются версией в bootstrap-скрипте. Обновление — отдельная задача с тестом.
- **C9. Кто заметит падение.** Внешний healthcheck (например, uptime-сервис), который пишет в Telegram при тишине. Telegram-бот отправляет «жив» раз в сутки.
- **C10. Тестовый режим.** Dry-run: задача проходит весь путь на тестовом репозитории, без реального пуша в боевой и без мерджа. Запускается по команде `dry_run` и обязателен перед включением нового workspace.
- **C11. Стоимость простоя.** Песочницы, которые простаивают в `active`, переводятся в `paused` по таймауту простоя. Счётчик простоя ведётся сервером.
- **C12. Изменение workspace во время задачи.** Задача фиксирует версию настроек в момент старта. Изменения применяются к следующим задачам.
- **C13. Спецификация в двух местах.** Источник правды — файл спецификации в репозитории. `SpecItem` в БД — зеркало. При расхождении побеждает репозиторий, расхождение пишется в журнал.

## 17. Открытые вопросы [MVP: блокирует только вопрос 3]

Вопрос 3 (GitHub или GitLab) блокирует MVP. Остальные вопросы позже, кроме вопроса 15 (утверждение спецификации): решить до запуска, нужен ли он.

1. Распознавание речи: какой STT-провайдер (Whisper через Polza, если доступен, или отдельный API).
2. Привязка песочницы: через тип агента (рекомендуется) или через конкретную.
3. GitHub или GitLab.
4. Клонирование репозиториев: при создании или при первой задаче.
5. Стоимость паузы у Novita.
6. Кастомные образы у Novita: можно ли запечь установку.
7. Продление сессии песочницы при таймауте по умолчанию.
8. Остановка агента по бюджету в процессе: внешний счётчик, таймаут exec или обёртка запуска.
9. Одно сообщение с этапами или отдельные сообщения на каждый этап (рекомендую одно, с редактированием).
10. Авто-мердж: сразу в main или сначала в staging с подтверждением.
11. Пауза песочницы и правило очистки. Сейчас правило «очистка перед паузой» требует удалить worktree. Предлагается: креды стираются всегда, worktree остаётся. Незакоммиченную работу при паузе сохранять как WIP-коммит в `task/<id>` (рекомендую) или оставлять как есть.
12. Надёжность Polza на командах управления: «срочно» и «все» должны всегда давать подтверждение или запускаться на безопасной стороне. Нужно решить, какие команды Polza может выполнить без кнопки.
13. Codex и skills: как Codex находит skills (отдельная папка, `AGENTS.md` или только через MCP). Если Codex не умеет подгружать skills сам, `get_skill` должен быть для него основным путём.
14. Обновление skill во время работы: агент на середине задачи берёт новую версию или дорабатывает со старой. Рекомендую: новая версия применяется на следующем этапе, текущий этап дорабатывается со старой.
15. Согласование спецификации. Сейчас задачи из `backlog` уходят в реализацию сразу после планирования. Вариант: спецификация ждёт кнопки «Утвердить» в Telegram, и только потом задачи становятся доступны агентам. Рекомендую кнопку для первых задач, потом можно отключить.
16. Что значит «Cloud с OpenSpec». В ТЗ принято как Claude Code с OpenSpec внутри песочницы. Если имелось в виду другое, это меняет раздел 5.0.
