# Критерии

## Приёмочные (из PLAN.md, раздел 17)

MVP принят, если:

1. Есть сервер и Harness как независимые компоненты.
2. Сервер с панелью и PostgreSQL разворачивается в Dokploy.
3. В панели создаётся проект и агент.
4. Есть раздел Skills с категориями и карточками.
5. Skills назначаются конкретному агенту.
6. `harness init <project_id>` подключает агент через одноразовый код.
7. После установки создаётся только `workflow/`.
8. В Harness нет жёсткой логики Git, Dokploy, деплоя, фреймворка.
9. Задача отправляется голосом в Telegram.
10. Голос превращается в задачу в панели.
11. Агент получает задачу, использует skills, отдаёт план.
12. План можно улучшать неограниченно.
13. До подтверждения плана код не меняется.
14. После подтверждения — реализация, проверки, отчёт.
15. Пользователь может принять, вернуть на доработку или оставить без публикации.
16. Push и deploy — только после явного принятия.
17. Прогресс и результат идут через REST или MCP.
18. Панель показывает задачи, статусы, агента, план, прогресс, skills, тесты, публикацию.
19. При ошибке задача сохраняет историю, отчёт и checkpoint.
20. Секреты не попадают в Git, логи, skills, YAML, отчёты.

## Качественные критерии проекта

Это наши внутренние требования, PLAN.md их не задаёт.

### Структура

- Файл кода ≤ 150 строк, одна ответственность.
- Слой API тонкий: маршрут → схема → сервис → репозиторий.
- Нет god-объектов и «портянок» из функций.
- Общая логика MCP и REST живёт в одном service layer.

### Расширяемость

- Новый вид работы добавляется skill'ом, без правок `harness/` и `server/`.
- Новая категория skills — данные, а не код.
- Провайдер транскрибации заменяется переменной окружения.
- Новая интеграция публикации — новый skill, не новая ветка кода.

### Надёжность

- Любое действие агента идемпотентно по ключу события.
- Потеря аренды не теряет работу: checkpoint остаётся на сервере.
- Ошибка публикации фиксируется событием, задача остаётся принятой.
- Все переходы статусов проверяются на сервере, а не на Harness.

### Безопасность

- Токены — только хеши в БД, показываются один раз.
- Агент видит только свой проект и свою задачу.
- Агент не может сам подтвердить план, принять результат, поставить `merged`.
- Секреты только в окружении Dokploy.

### Удобство

- Путь от голосового сообщения до плана — минуты, без терминала.
- Панель отвечает на вопрос «что сейчас происходит» с одного экрана задачи.
- Ошибки в Telegram описаны человеческим языком и содержат следующий шаг.

## Как проверяем

| Критерий | Проверка |
|---|---|
| Сквозной поток | ручной прогон сценария из MVP.md |
| Права агента | попытка чтения чужой задачи и `merged` через MCP → отказ |
| Идемпотентность | повтор запроса с тем же ключом не создаёт дубликат |
| Аренда | остановка harness → задача уходит в `stalled` |
| Skills | изменение skill во время задачи не влияет на текущую |
| Секреты | `grep` по репозиторию и логам не находит токенов |
