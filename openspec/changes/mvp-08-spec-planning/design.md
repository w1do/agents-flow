# Design: mvp-08-spec-planning

## Context

Планировщик — Claude Code с OpenSpec внутри песочницы (вопрос 16). Источник правды — файлы в репозитории,
`spec_items` — зеркало (ТЗ §10.1, C13).

## Goals / Non-Goals

**Goals:** итог планирования проверяется механически; после `ready` задачи реализации уже в `backlog`.

**Non-Goals:** качество декомпозиции оценивает человек по MR, не сервер.

## Decisions

- **Сервер проверяет результат, а не верит отчёту.** `completed` от планировщика лишь запускает проверки; отсутствие
  каталога изменения, провал `openspec validate` или ноль задач → `error` с причиной.
- **Пункт спецификации = самостоятельно проверяемая часть работы** (обычно группа `##` в `tasks.md`); ключ пункта —
  `<change_id>#<номер группы>`. Это даёт стабильный ключ для `sync_spec`.
- **Ветка плана пушится без MR** (D-10): исполнители берут её как базу, и спецификация попадает в основную ветку
  с первым MR реализации.
- **Секреты:** `secret_scan` прогоняет `git diff origin/<base>...HEAD` через `security/redaction` с точными
  значениями выданных кредов; находка блокирует push, задача `error` без текста секрета в причине.
- **Push идемпотентен:** если `git ls-remote` показывает тот же хеш — шаг пропускается.

## Risks / Trade-offs

- [Планировщик создаёт задачи, но падает до коммита] → проверки сервера отклоняют план; созданные задачи переводятся в `trash` той же транзакцией, что и `error` плана.
- [Слишком мелкая или крупная декомпозиция] → правила в промпте (задача ≤ 2 часов, 1–7 задач); ревью MR человеком.
