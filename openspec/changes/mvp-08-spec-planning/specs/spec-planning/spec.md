## ADDED Requirements

### Requirement: Работа начинается со спецификации

После выбора проекта задача `plan` SHALL выполняться планировщиком в песочнице, который создаёт OpenSpec-изменение
в ветке `task/<plan_id>`. Задачи реализации MUST появляться только как результат планирования.

#### Scenario: Мелкая правка

- **WHEN** владелец просит «поправь опечатку в заголовке» и выбирает проект
- **THEN** сначала выполняется задача `plan` и создаётся спецификация, а не сразу правка

### Requirement: Механическая проверка плана

Задача `plan` SHALL переходить в `ready` только если в ветке есть новое изменение OpenSpec, оно проходит
проверку формата, создана хотя бы одна задача `implement` и в diff нет секретов. Иначе задача MUST переходить
в `error` с причиной, а созданные ею задачи — в `trash`.

#### Scenario: Спецификация не проходит проверку

- **WHEN** планировщик сообщил `completed`, но проверка OpenSpec завершилась ошибкой
- **THEN** задача `plan` в `error` с причиной, её задачи `implement` в `trash`, ветка не пушится

#### Scenario: Секрет в спецификации

- **WHEN** в diff плана найден токен
- **THEN** push не выполняется, задача в `error`, причина не содержит значения токена

### Requirement: Итог планирования в Telegram

При успешном планировании сообщение задачи SHALL получить строку «спецификация готова, задач: N» и список
кратких названий задач реализации.

#### Scenario: Три задачи

- **WHEN** планировщик создал три задачи реализации и проверки прошли
- **THEN** в сообщении задачи строка «спецификация готова, задач: 3» и три названия

### Requirement: Зеркало спецификации

Пункты спецификации SHALL храниться в базе со ссылкой на изменение OpenSpec и задачу плана; каждая задача
`implement` MUST ссылаться на свой пункт.

#### Scenario: Связь задачи и пункта

- **WHEN** открыта задача реализации
- **THEN** у неё есть ключ пункта спецификации и идентификатор задачи плана
