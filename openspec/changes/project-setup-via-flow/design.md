# Design

## Context

Сейчас проект описан блоком `workspaces` в `harness.yaml` (File Mount на сервере в Dokploy). Машина агента
получает его через `agent init`, который пишет в `~/.harness` и `~/work/<project>`. Значит, одна настройка
живёт в двух местах и правится руками. Change `local-agent-machine` (в работе) уже переносит выполнение на
машину агента и вводит `agent init <project>`. Этот change задаёт, откуда `agent init` берёт настройки.

Ключевое ограничение из `platform-config` и `sandbox-profile`: ключи в конфиге и в БД не хранятся, только
ссылки `vault:...`. Значение ключа получает только процесс, которому оно нужно.

## Goals / Non-Goals

**Goals:**
- Один источник настроек проекта: таблица проектов на сервере.
- `agent init <workspace>` создаёт локальную папку проекта по серверной записи, без ручной правки.
- Бот и консоль работают через один сервис проектов (правило `Telegram-кнопка и MCP-инструмент вызывают
  одну и ту же функцию сервиса`).

**Non-Goals:**
- Сама консоль (`apps/console`, `mvp-10`): здесь только API, на который она опирается.
- MCP-инструменты для проектов (после `operator-tokens`).
- Миграция `sandbox-profile`: его заменяет `local-agent-machine`.

## Decisions

1. **Хранение: таблица `projects` в Postgres.** Поля — как у `repo`/workspace из `platform-config`, плюс
   `status` (`active`/`disabled`) и время изменения. Миграция Alembic в `db/migrations`.
   Альтернатива — оставить `harness.yaml` и только генерировать его: отвергнуто, потому что два источника
   снова появляются.

2. **Сервис `services/projects`** — единственный вход для записи и чтения. API `/api/console/projects`
   и бот вызывают его же. Валидация Pydantic до ORM (правило проекта).

3. **Выдача машине агента: `GET /api/projects/{id}/settings`** под операторским токеном (`HARNESS_ADMIN_TOKEN`,
   как сейчас для `/tasks`). Ответ — только поля для локального конфига, без значений ключей. Альтернатива —
   отдавать полный конфиг файлом: отвергнуто, потому что файл станет точкой утечки.

4. **`agent init <workspace>` берёт настройки по сети.** Адрес сервера (`HARNESS_PUBLIC_URL`) и токен — из ENV
   машины агента, не из файлов. Локальный harness-конфиг пишется в `~/.harness/projects/<id>.yaml` (права
   0600) и помечается как сгенерированный, с предупреждением «не править руками».
   Альтернатива — класть в `~/work/<project>`: отвергнуто, потому что репозиторий проекта может быть
   чужим и попасть в коммит.

5. **Идентификатор — `workspace`, не UUID.** Внутренний UUID сервера не используется в командах машины, чтобы
   оператор видел имя проекта. Уникальность `id` обеспечивается в БД.

6. **Переход боевого сервера.** `harness.yaml` с `workspaces` перестаёт загружаться. Существующие проекты
   переносятся в таблицу отдельным шагом (миграция данных и инструкция в `docs/deployment.md`), до выката
   образа с новым кодом.

## Risks / Trade-offs

- **Зависимость от `local-agent-machine`.** Пока тот change не слит, `agent init` не умеет тянуть настройки с
  сервера. Порядок: сначала слияние `local-agent-machine`, потом этот change.
- **Сетевой доступ машины агента к серверу.** `agent init` зависит от доступности `HARNESS_PUBLIC_URL`.
  Без неё проект не инициализируется; сообщение об ошибке должно это сказать.
- **Боевая миграция.** Переход с `harness.yaml` ломает старт сервера, если данные не перенесены. Поэтому
  выкат только после переноса проектов в БД (пункт 6).
- **Токен оператора.** Настройки проекта доступны по тому же токену, что и `/tasks`. Отдельный токен машины
  агента — возможное улучшение, в этот change не входит.
