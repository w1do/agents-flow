# Design

## Context

Worker (`apps/server/src/harness_server/worker/`) сейчас вызывает сервисы очереди и песочниц напрямую, а они
работают с `AsyncSession`. Чтобы worker жил на машине агента, эти вызовы заменяются HTTP-вызовами. Сами сервисы
остаются на сервере и не меняют правил переходов статусов.

## Goals / Non-Goals

**Goals:**
- Worker не импортирует модели БД и не открывает `DATABASE_URL`.
- Все правила очереди, статусов и токенов остаются в `services/`.
- Эндпоинты тонкие: Pydantic на входе, вызов сервиса, перевод доменных ошибок в ответы.

**Non-Goals:**
- Перенос песочниц или агентских процессов на сервер или обратно.
- Новые статусы задачи: используется только `domain/statuses.py`.
- Консоль и Telegram.

## Decisions

1. **Префикс `/worker`, отдельный роутер.** Отделяет канал worker от `/tasks` (оператор) и `/api/console`.
   Альтернатива: тот же `/tasks` с другим токеном. Отвергнуто: один роутер смешивает две модели доступа.

2. **Worker-токен из ENV, сравнение через `hmac.compare_digest`.** Токен не хранится в БД. Альтернатива:
   таблица токенов worker. Отвергнуто: лишняя таблица и миграция ради одного секрета на машину.

3. **Токен задачи (`task_tokens`) выдаётся при захвате.** Уже есть таблица `task_tokens` с ролями `planner`
   и `implementer`; роль берётся из типа задачи. Срок и отзыв — как у текущих токенов задачи (D-37).

4. **Захват через `SELECT ... FOR UPDATE SKIP LOCKED`** в сервисе очереди. Это уже принятый механизм
   `lock_next_task`; API только вызывает его и возвращает результат.

5. **Идемпотентность событий по ключу `(task_id, external_key)`.** Ключ передаёт worker. Уникальный индекс в
   миграции; повтор возвращает существующую запись.

6. **Heartbeat и `stalled` решает сервер.** Фоновая проверка на сервере переводит задачу в `stalled` по сроку
   последнего heartbeat. Worker не меняет статус по таймеру.

7. **Миграция:** новая таблица `task_events_keys` или уникальный индекс на `task_events` для ключа события;
   выбор фиксируется при реализации. Схема меняется только миграцией Alembic (CLAUDE.md §3).

## Risks / Trade-offs

- **Сеть между машиной агента и сервером.** Если сервер недоступен, worker не может отчитаться. Worker
  повторяет запросы с backoff; идемпотентность (решение 5) защищает от дублей.
- **Задачи, взятые до перехода.** Перед переключением очередь дренируется (процедура `docs/deployment.md`).
- **Утечка worker-токена.** Токен на машине агента лежит в ENV; при утечке оператор меняет его в ENV сервера
  и на машине агента. В БД токен не хранится, ротация не требует миграции.
