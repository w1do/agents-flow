# Design: mvp-04-telegram-intake

## Context

Webhook должен отвечать быстро, а STT может занимать секунды. Telegram повторяет доставку, если не получил `200`.

## Goals / Non-Goals

**Goals:** ни одного дубля задачи; ответ webhook < 1 с; никакой реакции на чужие чаты.

**Non-Goals:** голосовое управление, кнопки действий над задачей.

## Decisions

- **Приём и обработка разделены.** Webhook проверяет секрет и chat_id, вставляет `update_id` в
  `telegram_updates` (`ON CONFLICT DO NOTHING` через ORM `insert().on_conflict_do_nothing()`), ставит обработку
  в фоновую задачу (`BackgroundTasks`) и отвечает `200`. Альтернатива — обрабатывать синхронно: риск таймаута
  Telegram и повторной доставки во время STT.
- **Чужой chat_id** — `200` без ответа и без записи текста в БД (не даём сигнал, что бот жив).
- **callback_data** — `ws:<task_short>:<workspace_id>` до 64 байт; повторное нажатие на задачу не в `choosing`
  отвечает `answer_callback_query("уже выбрано")` без смены статуса.
- **Одно сообщение:** `notify.append_stage(task, line)` дописывает строку и вызывает `editMessageText`; ошибка
  «message is not modified» игнорируется; при недоступном сообщении отправляется новое и id обновляется.
- **STT:** файл скачивается в память (лимит размера из настроек), отправляется multipart; ошибка STT → ответ
  «не удалось распознать, пришлите текстом», задача не создаётся.

## Risks / Trade-offs

- [Фоновая задача потеряется при рестарте] → `telegram_updates.processed_at`; при старте worker дообрабатывает
  необработанные апдейты старше 1 минуты.
