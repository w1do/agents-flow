# Spec Delta

## Purpose

Ведёт задачу от создания до публикации: статусы, аренду, решения пользователя,
события и идемпотентность отчётов агента.

## ADDED Requirements

### Requirement: Создание задачи
Система SHALL создавать задачу в проекте со статусом `new`, сохраняя текст
источника и тип источника (`web`, `telegram_text`, `telegram_voice`, `api`).

#### Scenario: Задача из панели
- **WHEN** администратор создаёт задачу с названием и описанием
- **THEN** задача появляется в проекте со статусом `new`

#### Scenario: Задача из Telegram
- **WHEN** приходит распознанный текст голосового сообщения
- **THEN** создаётся задача с `source_type = telegram_voice` и текстом в `source_text`

### Requirement: Набор статусов задачи
Система SHALL использовать только статусы `new`, `choosing`, `planning`,
`backlog`, `active`, `testing`, `ready`, `merged`, `error`, `stalled`, `paused`,
`trash` и SHALL отклонять переходы вне разрешённого набора.

#### Scenario: Основной поток
- **WHEN** задача проходит аренду, план, реализацию и проверки
- **THEN** статусы сменяются в порядке `new → choosing → planning → backlog → active → testing → ready`

#### Scenario: Недопустимый переход
- **WHEN** агент пытается перевести задачу из `backlog` сразу в `merged`
- **THEN** сервер отвечает 409 и статус не меняется

### Requirement: Атомарная аренда задачи
Система SHALL выдавать агенту не более одной задачи со статусом `new` из его
проекта, выбирая её транзакционно, и SHALL записывать `assigned_agent_id`,
`lease_id` и срок аренды 60 секунд.

#### Scenario: Два агента одновременно
- **WHEN** два агента одновременно запрашивают задачу при одной доступной
- **THEN** задачу получает ровно один, второй получает пустой ответ

#### Scenario: Нет задач
- **WHEN** в проекте нет задач со статусом `new`
- **THEN** сервер отвечает успешно с пустым результатом, без ошибки

#### Scenario: Агент уже занят
- **WHEN** у агента есть незавершённая арендованная задача
- **THEN** новая задача не выдаётся

### Requirement: Продление аренды heartbeat
Система SHALL продлевать аренду на 60 секунд по heartbeat агента и SHALL
обновлять время последней активности.

#### Scenario: Heartbeat во время работы
- **WHEN** агент отправляет heartbeat до истечения аренды
- **THEN** срок аренды продлевается, задача остаётся за агентом

#### Scenario: Heartbeat без задачи
- **WHEN** агент отправляет heartbeat без аренды
- **THEN** сервер отвечает успешно и обновляет статус агента на `online`

### Requirement: Переход в stalled по истечении аренды
Система SHALL переводить задачу в `stalled` при истечении срока аренды
и SHALL позволять вернуть её в работу только администратору.

#### Scenario: Агент пропал
- **WHEN** с последнего heartbeat прошло больше срока аренды
- **THEN** задача получает статус `stalled`

#### Scenario: Агент вернулся после истечения
- **WHEN** агент присылает отчёт с прежним `lease_id` после перехода в `stalled`
- **THEN** сервер отвечает 409, работа не продолжается

#### Scenario: Возобновление
- **WHEN** администратор возвращает задачу из `stalled` в `new`
- **THEN** задача снова доступна для аренды

### Requirement: Проверка lease во всех отчётах
Система SHALL требовать актуальный `lease_id` в каждом отчёте агента и SHALL
отвечать 409 при устаревшем или чужом lease.

#### Scenario: Чужой lease
- **WHEN** агент присылает отчёт с `lease_id` задачи другого агента
- **THEN** сервер отвечает 409 и ничего не меняет

### Requirement: Приём плана и решение пользователя
Система SHALL принимать `plan_text` от агента, переводить задачу в `backlog`
и SHALL менять её статус только по решению администратора `approved` или `rejected`.

#### Scenario: План передан
- **WHEN** агент присылает план в статусе `planning`
- **THEN** задача переходит в `backlog` и план становится доступен пользователю

#### Scenario: План одобрен
- **WHEN** пользователь выбирает `approved`
- **THEN** задача переходит в `active`, и агент может начать реализацию

#### Scenario: План отправлен на улучшение
- **WHEN** пользователь выбирает `rejected` с замечанием
- **THEN** задача возвращается в `planning`, `plan_revision` увеличивается,
  замечание сохраняется в `plan_feedback`

#### Scenario: Агент не может одобрить свой план
- **WHEN** агентский токен вызывает решение по плану
- **THEN** сервер отвечает 403

### Requirement: Приём результата и решение пользователя
Система SHALL принимать отчёт о реализации и результаты проверок, переводить
задачу в `ready` и SHALL разрешать публикацию только по решению `publish`.

#### Scenario: Результат передан
- **WHEN** агент присылает итог с изменёнными файлами и результатами тестов
- **THEN** задача переходит в `ready`, отчёт виден в карточке

#### Scenario: Принять и опубликовать
- **WHEN** пользователь выбирает `publish`
- **THEN** сервер ставит `merged` и передаёт агенту этап публикации

#### Scenario: Оставить без публикации
- **WHEN** пользователь выбирает `keep_ready`
- **THEN** задача остаётся в `ready`, публикация не запускается

#### Scenario: Доработать
- **WHEN** пользователь выбирает `rework` с замечанием
- **THEN** задача возвращается в `active`, замечание видно агенту

#### Scenario: Агент не может поставить merged
- **WHEN** агентский токен пытается сменить статус на `merged`
- **THEN** сервер отвечает 403

### Requirement: Лента событий задачи
Система SHALL записывать каждое значимое действие агента и пользователя
в `task_events` только добавлением, с типом, сообщением и необязательным payload.

#### Scenario: Прогресс и тесты
- **WHEN** агент присылает прогресс и результаты проверок
- **THEN** в ленте появляются события с временем и типом

#### Scenario: События не перезаписываются
- **WHEN** задача переходит в `error`
- **THEN** ранее записанные события остаются без изменений

### Requirement: Идемпотентность REST-запросов
Система SHALL требовать `Idempotency-Key` для изменяющих состояние запросов
и SHALL возвращать сохранённый ответ при повторе с тем же ключом.

#### Scenario: Повтор создания
- **WHEN** запрос создания задачи приходит дважды с одним `Idempotency-Key`
- **THEN** создаётся одна задача, второй ответ совпадает с первым

#### Scenario: Другой ключ
- **WHEN** тот же запрос приходит с новым ключом
- **THEN** операция выполняется как новая

### Requirement: Идемпотентность отчётов агента по event_id
Система SHALL требовать `event_id` на каждый отчёт агента и SHALL игнорировать
повтор с уже известным `event_id`.

#### Scenario: Повтор отчёта
- **WHEN** агент повторяет отчёт после сетевой ошибки с тем же `event_id`
- **THEN** дубликат события не создаётся, ответ успешен

### Requirement: Сохранение состояния при ошибке
Система SHALL сохранять историю, отчёт и checkpoint при переходе задачи
в `error` или `stalled`.

#### Scenario: Агент сообщил ошибку
- **WHEN** агент отправляет `fail` с текстом ошибки
- **THEN** задача получает `error`, событие сохраняется, checkpoint не теряется

#### Scenario: Возобновление после сбоя
- **WHEN** задача снова выдана агенту с сохранённым checkpoint
- **THEN** агент получает checkpoint в состоянии задачи
