# Design

## Context

Кода нет: `server/`, `harness/` и `deploy/` содержат только README. Есть
утверждённые ТЗ и документация, по которым нужно собрать прототип. Требования
и поведение описаны в `specs/` рядом; мотивация — в `proposal.md`.

Ограничения, задающие подход:

- Один репозиторий, два deployable-компонента и один общий API-контракт.
- Прототип нужен быстро: сначала сквозной путь, потом качество деталей.
- Внешние ключи (Telegram, транскрибация, LLM) появятся позже; система должна
  подниматься и проходить сквозной сценарий без них.
- Файл кода ≤ 150 строк, одна ответственность.
- Код пишут суб-агенты по чётко разделённым путям, поэтому границы модулей
  должны быть заранее определены и не пересекаться.

## Goals / Non-Goals

**Goals:**

- Поднимаемый одной командой сервер: база, миграции, API, панель, MCP.
- Проверяемый без внешних сервисов сквозной путь задачи.
- Harness, который запускается в любом Git-проекте и не знает стека.
- Контракт API, стабильный для обоих компонентов и пригодный для тестов.

**Non-Goals:**

- Промышленная надёжность: бэкапы, метрики, трейсинг, ретраи публикации.
- Многопользовательность, роли, несколько агентов на проект одновременно.
- WebSocket, очереди, собственный оркестратор.
- Готовый UX-дизайн панели за пределами пяти экранов.

## Decisions

### 1. Структура репозитория

`server/app/{api,mcp,services,repositories,models,schemas,integrations,core}`,
`server/web`, `server/migrations`, `server/tests`; `harness/cmd/harness`,
`harness/internal/{config,api,leases,skills,workspace,agent}`;
`runner/` — отдельный Python-пакет этапов агента, `deploy/`.

Альтернатива: три независимых репозитория по ТЗ. Отклонено для прототипа:
лишние шаги публикации и версионирования; границы папок уже совпадают
с будущим разделением.

### 2. Слои сервера

Маршрут → Pydantic-схема → service → repository → SQLAlchemy. MCP-инструменты
вызывают те же сервисы. Правила переходов статусов живут в одном модуле
`services/task_transitions.py`, поэтому REST, MCP, Telegram и панель не могут
обойти проверку.

Альтернатива: отдельные сервисы для MCP и REST. Отклонено: разошлись бы
проверки lease и прав.

### 3. Аренда через advisory-подход на `FOR UPDATE SKIP LOCKED`

`claim` — одна транзакция: `SELECT ... WHERE project_id = :p AND status = 'new'
ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1`, затем запись lease.
Проверка «агент уже занят» выполняется в той же транзакции через
`SELECT ... WHERE assigned_agent_id = :a AND status IN (...)`.

Альтернатива: оптимистичная блокировка по `updated_at`. Отклонено: гонки
при двух одновременных claim'ах.

### 4. Идемпотентность

REST: `Idempotency-Key` + таблица `idempotency_keys` с уникальным
`(scope, idempotency_key)`; повтор возвращает сохранённый код и тело.
MCP: обязательный `event_id`, уникальный индекс `(task_id, event_id)`
в `task_events`. Обе схемы используют один и тот же резолвер повторного ответа.

Альтернатива: только `event_id` везде. Отклонено: REST-создание задачи не
привязано к задаче, ему нужен собственный ключ.

### 5. Транскрибация

Абстракция `Transcriber.transcribe(path) -> str`, выбор реализации по
`TRANSCRIPTION_PROVIDER` (`openai`, `stub`). `stub` возвращает заранее
заданный текст и нужен, чтобы прогнать голосовой сценарий без ключа.
Провайдер `openai` — OpenAI-совместимый `/audio/transcriptions`
с `OPENAI_BASE_URL` и `OPENAI_API_KEY`.

### 6. Telegram

`python-telegram-bot` в режиме webhook-обработчика внутри FastAPI: приём
update, маршрутизация по `project.telegram_chat_id`, отправка сообщений через
Bot API напрямую. Решения — callback-кнопки, вызывающие тот же сервис, что
панель. Если `TELEGRAM_BOT_TOKEN` пуст, модуль не подключается и REST работает.

### 7. Запуск агента: отдельный runner, а не код в Harness

Harness запускает внешнюю команду из `workflow/config.yaml`
(`agent_command`, по умолчанию `python -m runner`), передаёт JSON-вход в stdin
и читает JSON-события из stdout. Внутри `runner/` — этапы и Deep Agents.

Почему так: Go-бинарник остаётся без знаний о фреймворках агента; runner
переиспользует Python-экосистему; контракт stdin/stdout тестируется без LLM.

Runner поддерживает два режима: `AGENT_PROVIDER=stub` — детерминированные
план и результат без сети (нужен для сквозного прогона сразу); `deepagents` —
реальный Deep Agents через OpenAI-совместимый API (`OPENAI_API_KEY`,
`OPENAI_BASE_URL`, `AGENT_MODEL`).

Альтернатива: встроить LangChain в Go через HTTP. Отклонено: двойная работа
и лишняя зависимость от формата.

### 8. Worktree и ветка

`git worktree add ../<repo>-task-<short-id> -b task/<task_id>` от текущего HEAD.
Путь и ветка запоминаются в `task.checkpoint.worktree`; повторный запуск задачи
переиспользует существующий каталог. Основная копия не изменяется.

### 9. Панель

React + TypeScript + Vite + Tailwind (shadcn-стиль, минимум компонентов),
собирается в `server/web/dist` и раздаётся FastAPI как static. API вызывается
по `/api/v1` тем же origin, поэтому CORS не нужен. Авторизация — JWT
в `localStorage`, редирект на `/login` при 401.

Альтернатива: серверный рендеринг на Jinja. Отклонено: ТЗ требует React,
а SPA проще в пяти экранах.

### 10. Схема БД одной миграцией

Одна Alembic-миграция создаёт все таблицы ТЗ и индексы. Enum-поля — текстовые
с CHECK-ограничениями: проще в прототипе и не требует миграции типа при
добавлении статуса.

### 11. Конфигурация и `.env`

`pydantic-settings`, значения по умолчанию для локального запуска, чтобы
`docker compose up` работал без правки. `.env.example` содержит все имена;
локальный `.env` заполняется агентом тестовыми значениями, реальные ключи
подставляет пользователь. `JWT_SECRET` и `ADMIN_PASSWORD` генерируются случайно
при первом заполнении и не печатаются в ответах.

### 12. Порядок реализации суб-агентами

Одна задача `agents-flow-mvp`, внутри — три независимых блока по путям:

1. `server/` API, модели, миграции, сервисы, тесты (Sol → Terra → Astra).
2. `harness/` + `runner/` (Sol → Terra → Astra), зависит от контракта API
   из блока 1, который фиксируется в `docs/api.md` на шаге 1.
3. `server/web/` панель (Sol → Astra), зависит только от REST-контракта.

Блоки 1 и 3 могут идти параллельно после создания схем API; блок 2 — после
блокировки контракта. Пересечений путей нет.

## Risks / Trade-offs

- [Прототип без LLM-ключей может «пройти» сценарий на заглушке, не проверив
  реального агента] → `stub` и `deepagents` используют один контракт runner,
  замена — переменная окружения; в `docs` фиксируется, что именно проверил stub.
- [Одна миграция на всю схему усложнит будущие изменения] → изменения далее
  отдельными миграциями; базовая уже соответствует ТЗ.
- [Панель на localStorage уязвима к XSS] → нет пользовательского HTML-рендера,
  Markdown отображается как текст; риск принят для прототипа.
- [Webhook без ретраев теряет сообщения при падении сервера] → Telegram
  повторяет доставку сам; ошибки пишутся в лог без содержимого.
- [Раннер агента выполняет команды из skills в рабочем каталоге] → работа
  только в worktree, запуск от текущего пользователя; изоляция контейнером
  вне рамок прототипа.
- [Три параллельных агента на одном репозитории конфликтуют по общим файлам]
  → блоки разделены по каталогам, общие файлы (`docs/`, `CLAUDE.md`) правит
  только оркестратор.

## Migration Plan

Развёртывание с нуля: заполнить `.env` из `.env.example`, `docker compose up`,
дождаться `migrate`, открыть панель и войти под `ADMIN_EMAIL`. Откат —
удаление volume базы; данных, которые нужно сохранять, в прототипе нет.

## Open Questions

- Нужен ли `harness` как отдельный бинарник для публикации в PATH или
  достаточно `go run ./cmd/harness` на время прототипа?
- Какой провайдер транскрибации будет основным на проде (OpenAI, Deepgram,
  локальный whisper) — влияет только на значение переменной.
