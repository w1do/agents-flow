# Design: gates-tests-deploy

## Context

D-58 задаёт три уровня гейтов. Уровень 1 — базовые гейты безопасности в коде (`mvp-09`, `CORE_GATES`), всегда и
без настроек. Уровень 2 — гейты проекта: `workspaces[].gates` (`preset` + переопределения) в `harness.yaml`, позже
в консоли. Уровень 3 — гейты задачи. Изменение расширяет уровни 2 и 3. Уровень 1 оно не трогает.

## Goals / Non-Goals

**Goals:** итоговый набор гейтов нельзя ослабить ни задачей, ни агентом, ни веткой задачи; пресеты покрывают
код, контент, данные и документацию; результат каждой проверки объективен (код возврата команды на сервере или
решение владельца), а не отчёт агента.

**Non-Goals:** настройка базовых гейтов; авто-мердж; редактор гейтов в консоли.

## Decisions

- **Пресет = шаблон.** `PRESETS: Mapping[str, tuple[str, ...]]`: `code` → (`tests`), `content` → (`owner_approval`),
  `data` → (`check`, `owner_approval`), `docs` → (`lint`, `owner_approval`), `none` → (`owner_approval`).
  Переопределения `test`, `lint`, `build`, `check` задают команды. Гейт с обязательной командой без неё → состояние
  `no_command` и `owner_approval`, «пройдено» не пишется. Альтернатива — произвольный список гейтов в конфиге (прежний
  план): допускал отключение проверок и ошибки порядка.
- **Объединение уровней.** `effective_gates = CORE_GATES ∪ project_gates ∪ repo_file_gates ∪ task_gates`, порядок
  задаёт фиксированный `GATE_ORDER` в коде. Конфиг уровня 3 описывается схемой только с полями добавления
  (`extra_checks: list[str]`, `require_owner_approval: bool = False`). Поля отключения в схеме нет, лишние поля
  отклоняются (`extra="forbid"`). Альтернатива — флаги `skip_*` с проверкой прав: ослабление было бы возможно при ошибке проверки.
- **Кто задаёт гейты задачи.** Владелец (Telegram, консоль) и планировщик через `create_task`. Исполнитель не
  задаёт: инструмента для этого у роли `implementer` нет. Агент не может ослабить собственные гейты.
- **Файл гейтов в репозитории** `.harness/gates.yaml` читается сервером через `git show origin/<default_branch>:.harness/gates.yaml`
  после `git fetch`, а не из worktree задачи. Правка этого файла в ветке задачи запрещена базовым `path_policy`
  (`.harness/**`, `mvp-09`). Файл может только добавить гейты. Альтернатива — читать из ветки задачи: агент
  ослабил бы проверки своей же правкой.
- **Деплой:** команда `deploy` из переопределений workspace, запуск в worktree после MR, нулевой код → `passed`;
  иначе `error`, MR не помечается готовым.
- **Skills** описывают агенту, как пройти проверки, но не участвуют в решении: гейт выполняет сервер.

## Risks / Trade-offs

- [Команда `check` у данных долгая] → таймаут, учёт процессов (`processes`).
- [Файл гейтов в основной ветке поменяли руками на более слабый] → он только добавляет к пресету workspace, ослабить
  пресет нельзя.
