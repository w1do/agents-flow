# Proposal: task-rework

> Доработка задачи по замечанию владельца и диалог с агентом через Telegram. Волна 1 (после MVP), см. PLAN.md.
> Приоритет владельца: **важно** (2026-10-19). Принцип (D-57): всё общение владелец ↔ харнесс ↔ агент идёт через
> Telegram; консоль позже показывает тот же диалог.

## Open questions (нужен ответ владельца до реализации)

У каждого вопроса есть вариант по умолчанию, на нём написан design.md. Если владелец выбирает другой вариант,
design.md правится до начала реализации.

1. **Что считать «расплывчатым» замечанием.** По умолчанию модель маршрутизации (Polza, D-55) оценивает, можно ли
   по тексту понять, что менять (`actionable`, `confidence`). Ниже порога `ROUTING_MIN_CONFIDENCE` или
   `actionable = false` бот спрашивает «Что именно поменять?». Уточнение даётся **один раз**: ответ на него
   принимается без повторной оценки. Без Polza бот не оценивает текст, а просит подтвердить кнопками
   «Доработать» / «Отмена». Вариант: всегда спрашивать подтверждение кнопкой, без модели.
2. **Доработка задачи с влитым MR.** По умолчанию создаётся связанная задача-продолжение `implement` в `backlog`:
   новая ветка `task/<new_id>` от основной ветки, новый MR, ссылка `followup_of_id` на исходную задачу. Исходная
   задача остаётся в `merged`. Вариант: отказ с просьбой описать изменение новой задачей.
3. **Предел циклов доработки.** По умолчанию `TASK_REWORK_MAX = 5` на задачу. На шестом замечании бот отказывает и
   предлагает новую задачу. Вариант: другое число или без предела.
4. **Замечание, пока задача ещё в работе** (`backlog`, `active`, `testing`). По умолчанию замечание сохраняется и
   уходит агенту при следующем запуске; если задача дошла до `ready`, а непереданное замечание есть, харнесс сам
   возвращает её в работу (это засчитывается как цикл доработки). Вариант: только сохранять, в работу возвращает владелец.
5. **Где ждёт агент ответа владельца (отступление от D-56).** **Отвечен владельцем 2026-10-19: WIP-push при паузе —
   да, но с защитными гейтами ядра.** Агент не ждёт: он вызывает `ask_owner`, коммитит и завершает прогон. Харнесс
   проводит по ветке **все базовые гейты безопасности D-58** — `secret_scan`, `path_policy`, `diff_limits`,
   `branch_guard` (никогда `--force`, только `task/<id>`), — и только потом **пушит `task/<id>` без гейтов качества
   проекта (`tests`) и без MR** (WIP), очищает песочницу и ставит задачу в `paused`. После ответа задача идёт в
   очередь и продолжается с той же ветки. Ответ записан уточнением строки D-57 в docs/decisions.md (без нового
   номера). Отвергнутый вариант: песочница держит worktree без push до ответа, задача блокирует очередь.
6. **Напоминание о вопросе без ответа.** По умолчанию в этом изменении напоминаний нет, задача ждёт в `paused`
   сколько угодно. Вариант: одно напоминание через N часов (по образцу `routing-uncertainty`).
7. **Доработка задачи `plan`** (спецификации). По умолчанию не поддерживается: бот отвечает, что доработка
   доступна задачам реализации. Вопросы планировщика владельцу поддерживаются. Правка спецификации — `spec-approval`.
8. **Расходы.** Каждое замечание, привязанное ответом (reply) или кнопкой, — один платный вызов Polza на оценку
   ясности. Свободный текст стоит как раньше (один вызов классификации).

## Why

Владелец работает с харнессом через Telegram (2026-10-19: «раз у нас через тг всё идёт, то я должен общаться
через тг»). Сейчас любое сообщение становится новой задачей (`mvp-05`), а замечание к готовой работе («мне не
нравится, как ты сделал задачу») не связывается с задачей, её веткой и MR. Агент тоже не может спросить владельца:
`report_task` (`mvp-07`) знает только `started`, `progress`, `completed`, `failed`, и ответ некуда доставить.
ТЗ §5 и §5.0 требуют, чтобы голосовой путь через Telegram был основным. ТЗ §6 задаёт сообщения задачи, ТЗ §11 —
MCP агента.

## What Changes

- **Привязка сообщения к задаче (до классификации).** Ответ (Telegram reply) на любое сообщение бота о задаче
  (карточка, вопрос агента, уточнение, итог) привязывается к этой задаче без классификации. Ссылка `#<ref>`
  (последние 8 hex id задачи) в тексте тоже привязывает. Таблица `telegram_message_links` хранит связь
  «сообщение бота → задача».
- **Класс команды `feedback`** («замечание к задаче») в маршрутизации Polza. В промпт идут недавние задачи
  (`#ref` + краткое название). Модель возвращает до 3 кандидатов-задач и признак `actionable`. При уверенном
  кандидате замечание привязывается к нему, иначе бот присылает кнопки выбора задачи и «Это новая задача».
- **Доработка на той же ветке и в том же MR.** Задача `ready` или `error` с конкретным замечанием возвращается в
  `backlog`. Активация берёт существующую `origin/task/<id>`, агент получает замечание и историю, делает новые
  коммиты и вызывает «сдать работу» (D-56). Харнесс повторяет гейты, MR остаётся тем же (заметка в MR о доработке),
  в Telegram приходит «доработка N: готова, MR обновлён». Если MR уже влит, создаётся задача-продолжение.
- **Уточнение расплывчатого замечания.** Бот спрашивает «Что именно поменять?», ответ на этот вопрос завершает уточнение.
- **Кнопка «Доработать»** на сообщении задачи (`ready`, `error`, `merged`): бот просит написать, что поменять,
  ответом на его сообщение.
- **Вопрос агента владельцу.** Новый MCP-инструмент `ask_owner(question)` (роли `planner`, `implementer`). Вопрос
  приходит в Telegram отдельным сообщением. Ответ владельца (reply) записывается, задача из `paused` идёт в
  очередь, агент получает ответ в промпте следующего запуска.
- **Таблица `task_dialog`** — реплики диалога по задаче: вопрос агента, ответ владельца, замечание владельца. Из неё
  собирается история для агента, позже её показывает консоль.
- **Переходы статусов** только из набора ТЗ v5: `implement` `ready→backlog`, `active→paused`, `paused→backlog`;
  `plan` `planning→paused`, `paused→planning`. Новых статусов нет.

## Capabilities

### New Capabilities

- `task-dialog`: диалог по задаче (вопросы агента, ответы и замечания владельца), доработка, задача-продолжение.

### Modified Capabilities

- `command-routing`: ADDED — Привязка сообщения к задаче до классификации, Класс «замечание к задаче».
- `telegram-bot`: ADDED — Кнопка «Доработать», Вопрос агента в Telegram, Ссылки сообщений бота на задачу.
- `agents-flow-mcp`: ADDED — Вопрос владельцу.
- `delivery-gates`: ADDED — Доработка на той же ветке и в том же MR, Гейты считаются по прогону, Пауза до ответа
  владельца с базовыми гейтами безопасности.
- `task-lifecycle`: MODIFIED — Допустимые переходы (добавлены переходы доработки и ожидания ответа).

## Impact

- Зависит от: `mvp-09-delivery-mr` (ветка `task/<id>`, гейты, MR, адаптер `adapters/git` — GitLab или GitHub, D-60) и `mvp-07-agents-flow-mcp`
  (MCP, токен задачи, «сдать работу»). Использует `mvp-05-command-routing` (Polza, `routings`, уточнение) и
  `mvp-04-telegram-intake` (приём, `telegram_messages`).
- Согласуется с `telegram-full-stages`: кнопка «Доработать» добавляется в ту же клавиатуру сообщения задачи, что и
  «Остановить» / «Повторить». Какое изменение придёт вторым, то и дополняет общую функцию клавиатуры.
- Согласуется с D-58 (гейты в три уровня): у workspace с пресетом `none` готовую задачу принимает владелец
  кнопками «Принять» / «Доработать»; «Доработать» запускает поток доработки из этого изменения.
- Схема: миграция — таблицы `task_dialog`, `telegram_message_links`; колонки `tasks.followup_of_id`,
  `tasks.run_base_sha`, `routings.bound_via`; расширение CHECK `routings.command_class` (`feedback`) и
  `routings.decision` (`bound`).
- ENV: `TASK_REWORK_MAX` (по умолчанию 5). Docker Compose и `.env.example` — с разрешения владельца (агент `.env*` не читает).
- Документы: ARCHITECTURE.md (§3, §4, §5, §6, §9), docs/mcp-agents-flow.md (`ask_owner`), docs/glossary.md
  (`DialogEntry`, `MessageLink`, `feedback`, «доработка», «задача-продолжение»), docs/decisions.md (D-57, ответы на
  открытые вопросы — следующие свободные номера после D-58), PLAN.md.
- Ссылки: ТЗ §5, §5.0, §6, §10, §11, §14; D-13, D-18, D-31…D-34, D-55, D-56.

## Не входит

- Ожидание ответа внутри одного прогона агента (блокирующий `ask_owner`) — отвергнуто ответом на вопрос 5.
- Напоминания и истечение срока у вопросов без ответа — вопрос 6.
- Доработка задач `plan` и правка спецификации — `spec-approval`.
- Чтение диалога агентом через MCP (`get_task_dialog`) — история приходит в промпте.
- Показ диалога в консоли — после `mvp-10-operator-console`, отдельным изменением.
- Групповые чаты и несколько владельцев (D-30).
- Откат влитой задачи — `revert-task`.
- Продолжение сессии Claude Code (`--resume`) между прогонами — `agent-sessions`.
