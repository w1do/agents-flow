## ADDED Requirements

### Requirement: Токен задачи

Каждый вызов MCP SHALL требовать bearer-токен. Токен задачи MUST давать доступ только к инструментам своей роли
(`planner` или `implementer`) и только к своей задаче и своему workspace. Просроченный или отозванный токен MUST
отклоняться с ошибкой `unauthorized`.

#### Scenario: Токен после завершения задачи

- **WHEN** агент вызывает `report_task` токеном задачи, которая уже очищена
- **THEN** вызов отклоняется с `unauthorized`

#### Scenario: Исполнитель создаёт задачу

- **WHEN** агент с ролью `implementer` вызывает `create_task`
- **THEN** вызов отклоняется с `forbidden`, задача не создаётся

### Requirement: Отчёт о ходе задачи

Инструмент `report_task(status, text)` SHALL принимать `started`, `progress`, `completed`, `failed` и записывать
событие задачи. Отчёт `completed` от исполнителя MUST только запускать проверки сервера и MUST NOT сам переводить
задачу в `ready`. Текст MUST проходить фильтр секретов до записи.

#### Scenario: Агент закончил работу

- **WHEN** исполнитель вызывает `report_task("completed", "готово")`
- **THEN** появляется событие, задача переходит к проверкам сервера, статус `ready` выставляет только сервер

#### Scenario: Секрет в тексте отчёта

- **WHEN** текст отчёта содержит строку вида `glpat-…`
- **THEN** в событии и в Telegram значение заменено на `[REDACTED]`

### Requirement: Синхронизация спецификации

Инструмент `sync_spec(change_id, items)` SHALL создавать или обновлять пункты спецификации по ключу пункта в
workspace задачи и возвращать их идентификаторы. Повторный вызов с теми же данными MUST NOT создавать дубли.

#### Scenario: Повторная синхронизация

- **WHEN** планировщик дважды вызывает `sync_spec` с теми же пунктами
- **THEN** число пунктов не меняется, тексты актуальны

### Requirement: Создание задач реализации планировщиком

Инструмент `create_task(text, spec_item_key, priority?)` SHALL быть доступен только роли `planner` и создавать
задачу `implement` в статусе `backlog` в workspace задачи плана со ссылкой на пункт спецификации и на задачу плана.
Создать задачу другого kind, статуса или workspace MUST быть невозможно.

#### Scenario: Планировщик раскладывает работу

- **WHEN** планировщик вызывает `create_task` для трёх пунктов спецификации
- **THEN** в `backlog` появляются три задачи `implement` этого workspace, связанные с задачей плана

### Requirement: Чтение задач workspace

Инструмент `list_tasks(status?)` SHALL возвращать задачи только workspace токена.

#### Scenario: Чужой workspace

- **WHEN** в базе есть задачи двух workspace
- **THEN** агент видит только задачи своего workspace
