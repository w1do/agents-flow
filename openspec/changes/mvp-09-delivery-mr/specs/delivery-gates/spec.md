## ADDED Requirements

### Requirement: Задача реализации от очереди до MR

Задача `implement` SHALL браться из `backlog` по приоритету, выполняться исполнителем в ветке `task/<task_id>` и
после гейтов получать MR в основную ветку workspace. Сообщение в Telegram MUST получить строку «начата» при старте
агента и «готова, MR создан» со ссылкой на MR при успехе.

#### Scenario: Успешная задача

- **WHEN** исполнитель закоммитил изменения, тесты прошли
- **THEN** ветка запушена, создан MR, задача в `ready` со ссылкой на MR, в сообщении две строки этапов

### Requirement: Тесты не зелёные по умолчанию

Если у workspace не задана команда тестов, результат тестов SHALL быть «без тестов» и MUST NOT отображаться как
пройденный. Пройденными тесты считаются только по нулевому коду возврата заданной команды.

#### Scenario: Нет команды тестов

- **WHEN** у workspace нет `test_command`
- **THEN** задача получает отметку «без тестов», в сообщении нет слов «тесты пройдены»

#### Scenario: Тесты упали

- **WHEN** команда тестов вернула ненулевой код
- **THEN** задача в `error`, причина содержит хвост вывода без секретов, MR не создаётся

### Requirement: Секреты не уходят в репозиторий

Перед push система SHALL проверить diff ветки на шаблоны секретов и точные значения выданных на задачу кредов и
при находке MUST остановить доставку с причиной без значения секрета.

#### Scenario: Ключ в коде

- **WHEN** исполнитель добавил в код строку с API-ключом
- **THEN** push не выполняется, задача в `error`, в причине указан файл, но не значение

### Requirement: Идемпотентные гейты

Каждый гейт SHALL проверять, выполнен ли он уже. Повторный запуск после обрыва MUST продолжаться с первого
невыполненного шага и MUST NOT создавать второй MR для той же ветки.

#### Scenario: Обрыв после push

- **WHEN** worker перезапустился после успешного push, но до создания MR
- **THEN** push пропускается, создаётся один MR

#### Scenario: MR уже существует

- **WHEN** открытый MR из ветки `task/<id>` уже есть
- **THEN** новый MR не создаётся, задача ссылается на существующий

### Requirement: Нет изменений — нет готовности

Если исполнитель завершился без изменений относительно базы, задача SHALL перейти в `error` с причиной «нет изменений».

#### Scenario: Пустой результат

- **WHEN** агент завершился с кодом 0, но diff пуст
- **THEN** задача в `error` «нет изменений», MR не создаётся

### Requirement: Базовые гейты безопасности всегда

Гейты `commit_check`, `secret_scan`, `path_policy`, `diff_limits`, `branch_guard`, `push` и `merge_request` SHALL
выполняться для каждой задачи `implement` в коде сервера. Конфиг workspace, параметры задачи и действия агента
MUST NOT отключать, пропускать или ослаблять их (D-58). Проверка секретов MUST использовать шаблоны
`security/redaction` и точные значения секретов, выданных задаче, включая ключи из vault.

#### Scenario: Пресет без проверок

- **WHEN** у workspace пресет `none`
- **THEN** `secret_scan`, `path_policy`, `diff_limits` и `branch_guard` всё равно выполняются

#### Scenario: Ключ из vault в коде

- **WHEN** исполнитель вписал в файл значение ключа, разрешённого из vault для этой задачи
- **THEN** push не выполняется, задача в `error`, в причине файл без значения

### Requirement: Запрещённые пути и лимиты diff

Изменения в путях из списка запрещённых в коде (`.env*` кроме `.env.example`, приватные ключи, `.harness/`,
`.git/`, настройки Claude и MCP рабочего каталога) SHALL останавливать доставку с причиной «запрещённый путь».
Diff больше лимита по числу файлов или строк, а также бинарные файлы сверх лимита размера SHALL останавливать
доставку с причиной без содержимого.

#### Scenario: Агент изменил .env

- **WHEN** в diff задачи есть файл `.env.local`
- **THEN** задача в `error` «запрещённый путь: .env.local», push не выполняется

#### Scenario: Большой бинарный файл

- **WHEN** исполнитель добавил бинарный файл больше лимита
- **THEN** задача в `error` с размером и путём файла, push не выполняется

### Requirement: Push только в ветку задачи

Сервер SHALL пушить только в `refs/heads/task/<task_id>` явным refspec, без перезаписи истории. Ветка назначения,
совпадающая с основной веткой workspace или не начинающаяся с `task/`, MUST давать `error` до push.

#### Scenario: Попытка в основную ветку

- **WHEN** имя ветки назначения совпало с `default_branch`
- **THEN** push не выполняется, задача в `error`

### Requirement: Гейты качества проекта по пресету

Гейты качества SHALL браться из `workspaces[].gates` в `harness.yaml`: `preset` (`code` по умолчанию или `none`) и
переопределение `test`. Пресет `code` SHALL запускать команду тестов. Пресет `none` SHALL не запускать
автоматических проверок качества. Поле `test_command` SHALL читаться как синоним `gates.test`, а оба поля сразу
MUST отклоняться при загрузке конфига.

#### Scenario: Оба поля команды тестов

- **WHEN** у workspace заданы `test_command` и `gates.test`
- **THEN** конфиг не загружается, ошибка называет поле без значения

#### Scenario: Пресет по умолчанию

- **WHEN** у workspace нет раздела `gates`, а `test_command` задан
- **THEN** действует пресет `code` с этой командой тестов

### Requirement: Решение владельца без автоматических проверок

Если тесты не запускались (пресет `none` или `code` без команды), задача после MR SHALL получить `ready` с пометкой
о том, что автоматических проверок не было, и кнопкой «Принять». Нажатие SHALL записывать событие приёмки с
источником `telegram` без смены статуса. Сообщение MUST NOT говорить, что проверки пройдены. Отчёт агента о
проверках MUST NOT влиять на результат гейтов.

#### Scenario: Workspace без проверок

- **WHEN** задача workspace с пресетом `none` прошла базовые гейты
- **THEN** MR создан, задача в `ready`, в сообщении пометка «без автоматических проверок — нужно решение владельца» и кнопка «Принять»

#### Scenario: Агент сообщил о тестах

- **WHEN** агент в `report_task` написал «все тесты прошли», а команды тестов у workspace нет
- **THEN** `tests_state = no_tests`, в сообщении нет слов «тесты пройдены»
