# Design: mvp-03-task-store

## Context

Модель данных задана ТЗ §4 и ARCHITECTURE.md §3–4. Workspace в MVP — из `harness.yaml`, поэтому `workspace_id`
в таблицах — строка без внешнего ключа (D-11).

## Goals / Non-Goals

**Goals:** одна функция смены статуса для всех входов; очередь без гонок; каждая смена статуса видна в ленте.

**Non-Goals:** канбан-экран, операторские токены, архивация.

## Decisions

- **Машина статусов в `domain`** как словарь `(kind, from) → {to}`. Сервис вызывает `ensure_transition()`
  перед записью. Альтернатива — CHECK-ограничения в БД: сложно менять и не даёт понятной ошибки.
- **Статус хранится строкой с CHECK по набору ТЗ v5** (через SQLAlchemy `Enum(native_enum=False)`), чтобы
  добавление статуса требовало миграции. Альтернатива — нативный enum Postgres: дорогие миграции.
- **Каждая смена статуса = запись `task_events`** в той же транзакции. Telegram читает только события.
- **Очередь:** `select … where status in (…) order by priority desc, created_at for update skip locked limit 1`
  через ORM. Брокера нет (D-08).
- **Идентификаторы:** UUIDv7 (сортируемые по времени), в Telegram показываются короткие 8 символов.
- **Временный `HARNESS_ADMIN_TOKEN`** для `POST /tasks`/`GET /tasks/{id}`, сравнение `hmac.compare_digest`.
  Заменяется операторскими токенами (`operator-tokens`).

## Risks / Trade-offs

- [Ветвление статусов разрастётся] → все переходы в одной таблице с тестом «каждый статус достижим и из него есть выход либо он конечный».
