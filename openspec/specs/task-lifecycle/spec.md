## Requirements

### Requirement: Набор статусов задачи

Задача SHALL иметь kind из `plan`, `implement`, `check` и статус только из набора `new`, `choosing`, `planning`,
`backlog`, `active`, `testing`, `ready`, `merged`, `error`, `stalled`, `paused`, `trash`.
Система MUST отклонять запись любого другого значения и в сервисе (`invalid_status`), и в БД (CHECK).
Задачи kind `check` в MVP MUST отклоняться ошибкой `unsupported_kind`.

#### Scenario: Неизвестный статус

- **WHEN** сервис пытается установить статус `completed`
- **THEN** операция отклоняется ошибкой `invalid_status` и задача не меняется

#### Scenario: Неизвестный статус в обход сервиса

- **WHEN** в строку `tasks` напрямую записывают статус `completed`
- **THEN** база данных отклоняет запись нарушением ограничения `ck_tasks_status`

### Requirement: Начальный статус задачи

Новая задача `plan` SHALL создаваться в статусе `new`, задача `implement` — в статусе `backlog`. Создание задачи
MUST NOT создавать событие задачи. Указанный workspace MUST быть из `harness.yaml`, иначе создание отклоняется
ошибкой `unknown_workspace`.

#### Scenario: Задача реализации

- **WHEN** создаётся задача `implement` в известном workspace
- **THEN** задача имеет статус `backlog` и пустую ленту событий

### Requirement: Допустимые переходы

Смена статуса SHALL выполняться только по таблице переходов своего kind в `domain/statuses.py`. Для `plan`:
`new→choosing`, `choosing→planning`, `choosing→trash`, `planning→ready`, `planning→error`. Для `implement`:
`backlog→active`, `active→testing`, `active→error`, `testing→ready`, `testing→error`, `ready→merged`,
`error→backlog` (повтор). Недопустимый переход MUST отклоняться ошибкой `invalid_transition`.

#### Scenario: Пропуск этапа

- **WHEN** задачу `implement` в статусе `backlog` пытаются перевести в `ready`
- **THEN** возвращается `invalid_transition`, статус остаётся `backlog`, событие не создаётся

#### Scenario: Допустимый переход

- **WHEN** задачу `plan` в статусе `choosing` переводят в `planning`
- **THEN** статус меняется и появляется событие задачи со статусом `planning`

#### Scenario: Повтор после ошибки

- **WHEN** задачу `implement` в статусе `error` переводят в `backlog`
- **THEN** переход выполняется и задача снова доступна очереди

### Requirement: Лента событий

Каждая смена статуса и каждый отчёт агента SHALL создавать событие задачи с временем, статусом, текстом
и источником (`telegram`, `agent`, `worker`, `api`) в той же транзакции, что и изменение задачи.
Отчёт без смены статуса MUST записывать текущий статус задачи.

#### Scenario: История задачи

- **WHEN** задача прошла `backlog → active → testing → ready`
- **THEN** у задачи 3 события в хронологическом порядке со статусами `active`, `testing`, `ready`

#### Scenario: Отчёт без смены статуса

- **WHEN** агент добавляет отчёт к задаче в статусе `active`
- **THEN** появляется событие со статусом `active`, статус задачи не меняется

### Requirement: Очередь задач без гонок

Выбор следующей задачи SHALL возвращать задачу заданного kind и статуса с наибольшим приоритетом, а среди
равных — самую раннюю, переводить её в заданный статус с событием одним коммитом и MUST гарантировать, что два
конкурентных выбора не получат одну и ту же задачу (`FOR UPDATE SKIP LOCKED`).

#### Scenario: Два воркера

- **WHEN** два процесса одновременно запрашивают следующую задачу при одной задаче в `backlog`
- **THEN** задачу получает только один процесс, второй получает пустой результат

#### Scenario: Приоритет и порядок

- **WHEN** в `backlog` три задачи с приоритетами 0, 5 и 5
- **THEN** выбор возвращает сначала более раннюю задачу с приоритетом 5, затем вторую с приоритетом 5, затем задачу с приоритетом 0

#### Scenario: Занятая задача пропускается

- **WHEN** строка единственной задачи в `backlog` заблокирована другой транзакцией
- **THEN** выбор возвращает пустой результат, а после отката блокирующей транзакции получает эту задачу

### Requirement: HTTP-доступ к задачам

Сервер SHALL предоставлять `POST /tasks` (создание задачи `plan` в статусе `new` с текстом и необязательным
workspace, ответ `201`) и `GET /tasks/{id}` (задача, результат и события). Оба эндпоинта MUST требовать
bearer-токен `HARNESS_ADMIN_TOKEN` и отвечать `401` с заголовком `WWW-Authenticate: Bearer` при отсутствующем,
неверном или не настроенном токене до любой другой проверки; `404` — для неизвестной задачи; `422` — для
неизвестного workspace или пустого текста.

#### Scenario: Без токена

- **WHEN** запрос `GET /tasks/{id}` приходит без заголовка `Authorization`
- **THEN** сервер отвечает `401` и не раскрывает, существует ли задача

#### Scenario: Неверный токен

- **WHEN** запрос приходит с bearer-токеном, не совпадающим с `HARNESS_ADMIN_TOKEN`, или токен на сервере не задан
- **THEN** сервер отвечает `401`, задача не создаётся и не читается

#### Scenario: Создание задачи

- **WHEN** оператор отправляет `POST /tasks` с текстом и верным токеном
- **THEN** сервер отвечает `201` и возвращает задачу `plan` в статусе `new` с источником `api`
