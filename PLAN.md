# Техническое задание: Agents Flow MVP

## 1. Цель MVP

Создать работающий за один день вертикальный прототип Agents Flow.

Пользователь должен суметь:

1. Развернуть центральную панель у себя в Dokploy.
2. Создать в панели проект.
3. Создать или выбрать агента и назначить ему skills.
4. Установить Harness в любом Git-репозитории одной командой.
5. Отправить голосовую задачу в Telegram.
6. Получить от агента план.
7. Подтвердить план, попросить улучшить его или отклонить.
8. После подтверждения получить готовую реализацию и отчёт о проверках.
9. Принять работу, отправить на доработку либо оставить без публикации.
10. Только после приёмки разрешить агенту сделать Git push и/или деплой в Dokploy — исключительно по назначенным skills.
11. Видеть в панели ход работы по проекту: задачи, агента, статус, план, события, отчёт и итог публикации.

MVP не должен быть универсальной платформой автоматизации. Это минимальный рабочий поток «голосовая задача → план → два подтверждения → реализация → Git/Dokploy через skills».

## 2. Главный принцип

Система состоит из двух независимых репозиториев.

| Репозиторий | Назначение |
|---|---|
| `agents-flow-server` | Центральная панель, FastAPI API, PostgreSQL, Telegram, транскрибация и MCP. Разворачивается владельцем в Dokploy. |
| `agents-flow-harness` | Лёгкий клиент-исполнитель. Устанавливается в конкретный Git-проект и запускает готового агента Deep Agents. |

Harness — универсальный запускатель, а не система Git, Dokploy или разработки.

Harness не должен содержать жёстко зашитые функции:

- создания лендингов;
- работы с React, Laravel, FastAPI или иным стеком;
- Git commit/push;
- GitHub/GitLab;
- Dokploy;
- деплоя;
- тестирования конкретного проекта;
- конкретных команд инфраструктуры.

Вся логика конкретной работы передаётся агенту через skills.

```text
Harness:
получает задачу
→ получает назначенные skills
→ запускает Deep Agents
→ передаёт план и прогресс
→ ждёт подтверждений
→ передаёт результат

Skills:
объясняют агенту, как реализовать задачу,
проверить её, сделать push и выполнить деплой.
```

Не разрабатывать собственный LangGraph, брокер очередей, WebSocket-систему или отдельный движок оркестрации.

## 3. Архитектура

```text
Telegram: текст / голос
          │
          ▼
 FastAPI Server ───── PostgreSQL
     │       │
     │       ├── Web-панель
     │       ├── провайдер транскрибации
     │       └── MCP endpoint
     │
     └── HTTPS API
              │
     Agents Flow Harness
              │
     Deep Agents + Skills
              │
    локальный Git-проект
              │
 Git push / Dokploy deploy
    только после приёмки
```

### Центральный сервер

Технологии:

- Python;
- FastAPI;
- PostgreSQL;
- SQLAlchemy;
- Pydantic;
- Alembic;
- React + shadcn/ui;
- Docker Compose;
- Dokploy.

### Harness

Технологии:

- Go;
- один бинарный файл `harness`;
- YAML-конфигурация;
- Git как внешняя зависимость;
- готовый Deep Agents;
- REST API и MCP-клиент.

Harness не поднимает собственную базу, очередь или web-сервер.

## 4. Пользовательский сценарий MVP

### 4.1. Подготовка проекта

1. Администратор заходит в панель.
2. Создаёт проект, например `Landing`.
3. Создаёт или выбирает агента `landing-worker`.
4. Назначает агенту skills:
    - «Создание лендинга»;
    - «Frontend-проверки»;
    - «GitHub: commit и push»;
    - «Деплой в Dokploy».
5. В карточке проекта нажимает «Подключить Harness».
6. Панель создаёт одноразовый init-код.

### 4.2. Установка Harness

В корне Git-репозитория проекта пользователь запускает:

```bash
harness init <project_id>
```

Harness запрашивает одноразовый init-код, затем автоматически:

- определяет корень Git-репозитория;
- получает путь к проекту;
- читает Git remote;
- регистрирует агента;
- получает ограниченный agent token;
- создаёт папку `workflow/`;
- загружает назначенные skills;
- сохраняет конфигурацию.

После этого пользователь запускает:

```bash
harness run
```

### 4.3. Голосовая задача

1. Пользователь отправляет в Telegram голосовое сообщение: «Сделай простой лендинг для услуги».
2. Сервер распознаёт голос.
3. Создаёт текстовую задачу в проекте.
4. Harness арендует задачу.
5. Deep Agents получает:
    - текст задачи;
    - путь к локальному проекту;
    - назначенные skills;
    - текущий этап работы.
6. Агент создаёт план и передаёт его на сервер.
7. Telegram присылает план.

### 4.4. Первое подтверждение: план

В Telegram пользователь получает кнопки:

```text
✅ Приступай
✏️ Улучши план
🛑 Отклонить
```

- `Приступай` — агент начинает реализацию.
- `Улучши план` — агент получает замечание и готовит новый план.
- `Отклонить` — задача останавливается.

До нажатия `Приступай` агент не имеет права изменять код, выполнять Git push или деплой.

### 4.5. Реализация и второе подтверждение

После выполнения агент отправляет:

- краткий итог;
- изменённые файлы;
- результаты тестов;
- ссылку или SHA локального commit, если skill его создал;
- информацию о готовности к публикации.

Пользователь получает кнопки:

```text
✅ Принять и опубликовать
✏️ Доработать
⏸ Оставить без публикации
```

- `Принять и опубликовать` — агенту передаются skills Git push и Dokploy deploy.
- `Доработать` — задача возвращается в реализацию с замечанием.
- `Оставить без публикации` — результат остаётся готовым, но push и deploy не выполняются.

Агент запускает Git push и/или Dokploy deploy только после явного подтверждения публикации.

## 5. Статусы задач

Использовать только:

```text
new
choosing
planning
backlog
active
testing
ready
merged
error
stalled
paused
trash
```

Основной поток:

```text
new
→ choosing
→ planning
→ backlog
→ active
→ testing
→ ready
→ merged
```

Дополнительные переходы:

```text
backlog → planning   # пользователь попросил улучшить план
ready → active       # пользователь отправил на доработку
любой рабочий статус → paused / error / stalled / trash
```

Значение статусов:

| Статус | Значение |
|---|---|
| `new` | Задача создана, ожидает агента. |
| `choosing` | Агент арендовал задачу и готовит запуск. |
| `planning` | Агент формирует или улучшает план. |
| `backlog` | План ждёт решения пользователя. |
| `active` | Пользователь подтвердил план, идёт реализация. |
| `testing` | Агент запускает проверки из skill. |
| `ready` | Реализация готова, пользователь принимает или отправляет на доработку. |
| `merged` | Пользователь принял результат и разрешил публикацию. |
| `error` | Задача завершилась технической ошибкой. |
| `stalled` | Агент потерял связь или истекла аренда. |
| `paused` | Задача остановлена пользователем. |
| `trash` | Задача удалена из активной работы. |

Если Git push или деплой не удался после перехода в `merged`, задача остаётся принятой, а ошибка публикации фиксируется отдельным событием и в отчёте.

## 6. Skills

### 6.1. Назначение

Skill — Markdown-инструкция для Deep Agents.

Skill описывает, как выполнить конкретный вид работы. Он не является программным кодом Harness.

Примеры:

| Категория | Skills |
|---|---|
| Разработка | Создание лендинга, React-разработка, FastAPI-разработка |
| Ресёрч | Анализ конкурентов, подбор технологий |
| Тестирование | Проверки frontend, проверки Python-проекта |
| Git | GitHub: commit и push, GitLab: commit и push |
| Деплой | Деплой в Dokploy |
| Документация | Обновление README, подготовка отчёта |

### 6.2. Каталог Skills в панели

В панели должен быть раздел:

```text
/skills
```

Пользователь может:

- создать категорию;
- создать skill;
- изменить skill;
- отключить skill;
- открыть карточку skill;
- увидеть, каким агентам он назначен;
- назначить или снять skill у агента.

Skills распределяются по категориям, а назначаются конкретным агентам.

```text
Категория
  └── Skill
        └── назначается агенту
              └── загружается в Harness этого агента
                    └── передаётся Deep Agents при работе
```

### 6.3. Привязка Skills к агенту

Skills не назначаются автоматически всем агентам проекта.

Пример:

```text
Агент: landing-worker

Разработка
✓ Создание лендинга

Тестирование
✓ Frontend-проверки

Git
✓ GitHub: commit и push

Деплой
✓ Деплой в Dokploy
```

Это означает, что данный агент имеет право использовать только эти инструкции.

Если у агента нет skill Git или деплоя:

- он не делает push;
- он не деплоит;
- он заканчивает реализацию на этапе `ready`.

### 6.4. Версии Skills

Каждый skill имеет:

- название;
- категорию;
- описание;
- Markdown-содержимое;
- номер версии;
- хеш содержимого;
- статус активности.

При изменении текста skill увеличивается версия.

Для каждой задачи сохраняется снимок использованных skills:

- название;
- версия;
- хеш;
- категория.

Если skill меняется во время выполнения задачи, текущая задача использует старую версию. Новая версия применяется только к следующей задаче.

### 6.5. Ограничения Skills

- В skills запрещены секреты, пароли, API-ключи, токены и приватные SSH-ключи.
- Skill не выдаёт агенту реальных прав: доступ определяется окружением и токенами.
- Skill деплоя обязан требовать предварительного пользовательского подтверждения публикации.
- Harness не исполняет Markdown напрямую. Он передаёт skill готовому агенту как инструкцию.
- Все реальные действия агента отражаются в прогрессе и итоговом отчёте.

## 7. Установка Harness

### 7.1. Команда

```bash
harness init <project_id>
```

`project_id` не является секретом, поэтому для безопасного подключения требуется одноразовый init-код.

### 7.2. Получение init-кода

В панели проекта администратор нажимает «Подключить Harness».

Сервер выдаёт одноразовый init-код:

- привязан к одному проекту;
- действует 10 минут;
- применяется один раз;
- не даёт административных прав.

Harness может запросить код интерактивно или взять его из окружения:

```bash
AGENTS_FLOW_INIT_TOKEN=<одноразовый-код> harness init <project_id>
```

### 7.3. Структура после установки

```text
my-project/
└─ workflow/
   ├─ config.yaml
   ├─ .gitignore
   ├─ .agent-token
   └─ skills/
      ├─ development--landing.md
      ├─ testing--frontend.md
      ├─ git--github-push.md
      └─ deploy--dokploy.md
```

`workflow/.agent-token` добавляется в `.gitignore` и должен быть доступен только текущему пользователю.

### 7.4. Конфигурация

```yaml
server_url: https://flow.example.com
project_id: "uuid"
agent_id: "uuid"
workspace_path: "/absolute/path/to/project"
git_remote: "origin"
poll_interval_seconds: 5
lease_ttl_seconds: 60
```

Token не хранится в YAML.

### 7.5. Синхронизация Skills

При `harness init` агент получает все назначенные ему skills.

Перед получением каждой новой задачи Harness проверяет изменения:

- новые skills загружает;
- изменённые skills обновляет;
- снятые с агента skills удаляет локально;
- текущую уже выполняемую задачу не изменяет.

## 8. Deep Agents и Harness

### 8.1. Роль Harness

Harness выполняет только универсальные действия:

1. Проверяет и синхронизирует skills.
2. Отправляет heartbeat.
3. Атомарно арендует одну задачу.
4. Создаёт изолированный Git worktree и ветку `task/<task_id>`.
5. Запускает готового Deep Agents.
6. Передаёт ему задачу, путь к проекту, checkpoint и skills.
7. Передаёт серверу план, прогресс, результат и ошибки.
8. Ждёт решения пользователя по плану и результату.
9. Передаёт skills публикации агенту только после финального принятия.

### 8.2. Роль Deep Agents

Deep Agents:

- анализирует задачу;
- использует назначенные skills;
- формирует план;
- выполняет реализацию;
- запускает проверки;
- формирует отчёт;
- по разрешению пользователя использует skill Git и/или деплоя.

### 8.3. Разделение этапов и skills

| Этап | Передаваемые агенту skills |
|---|---|
| Планирование | Разработка, ресёрч, проектные инструкции |
| Реализация | Разработка, тестирование |
| Проверки | Тестирование |
| Публикация | Git и деплой, только после `Принять и опубликовать` |

## 9. Telegram и голосовой ввод

### 9.1. Поддерживаемые входы

- текстовая задача;
- Telegram `voice`;
- Telegram `audio`.

### 9.2. Голосовой поток

1. FastAPI получает Telegram webhook.
2. Для голосового сообщения получает файл Telegram.
3. Скачивает его во временный каталог.
4. Отправляет внешний сервис транскрибации.
5. При успехе создаёт задачу:
    - `source_type = telegram_voice`;
    - `source_text` — распознанный текст;
    - `description` — распознанный текст;
    - `status = new`.
6. Бот присылает пользователю распознанный текст и ссылку на задачу.
7. Временный файл всегда удаляется.

При ошибке транскрибации задача не создаётся. Бот просит повторить голосовое сообщение или написать задачу текстом.

### 9.3. Telegram-уведомления

Бот отправляет:

- распознанный текст голосовой задачи;
- план с кнопками подтверждения;
- уведомление о старте работы;
- отчёт о готовой реализации;
- запрос на принятие результата;
- итог Git push;
- итог деплоя;
- сообщение об ошибке или потере связи с агентом.

## 10. MCP

MCP нужен агентам как второй безопасный способ отчитываться о работе.

MCP endpoint:

```text
https://flow.example.com/mcp
```

Транспорт: Streamable HTTP по HTTPS.

MCP использует тот же FastAPI service layer и PostgreSQL, что REST API. Он не хранит отдельные статусы и не обходит ограничения API.

### MCP-инструменты MVP

| Инструмент | Назначение |
|---|---|
| `agent_get_assigned_task` | Получить текущую задачу, lease, checkpoint и пользовательские решения. |
| `agent_heartbeat` | Продлить аренду. |
| `agent_report_plan` | Передать план. |
| `agent_get_plan_decision` | Узнать, утверждён ли план. |
| `agent_report_progress` | Передать прогресс. |
| `agent_save_checkpoint` | Сохранить checkpoint. |
| `agent_report_test_result` | Передать результаты тестов. |
| `agent_report_result` | Передать итог реализации. |
| `agent_get_result_decision` | Узнать, принял ли пользователь результат. |
| `agent_report_publication_result` | Передать итог Git push или деплоя. |
| `agent_report_failure` | Передать ошибку. |

MCP-агент может работать только со своей арендованной задачей и своим проектом.

Он не может:

- читать задачи других проектов;
- подтверждать собственный план;
- принимать собственный результат;
- запускать публикацию без пользовательского решения;
- менять статус задачи на `merged` сам.

## 12. API-контракты

Базовый путь:

```text
/api/v1
```

Все изменяющие состояние REST-запросы требуют заголовок:

```text
Idempotency-Key: <UUID>
```

## 13. Аренда задач и идемпотентность

- Harness запрашивает задачу каждые 5 секунд.
- Один агент выполняет не больше одной задачи одновременно.
- Выбирается задача со статусом `new` из проекта агента.
- Аренда выполняется транзакцией PostgreSQL с `FOR UPDATE SKIP LOCKED`.
- При аренде записываются `assigned_agent_id`, `lease_id`, `lease_expires_at`.
- Время аренды: 60 секунд.
- Heartbeat продлевает аренду ещё на 60 секунд.
- Все события и отчёты должны содержать актуальный `lease_id`.
- Устаревший или чужой `lease_id` получает ошибку `409`.
- Если аренда истекла, задача становится `stalled`.
- Возобновить её может только администратор.
- Для MCP-отчётов обязателен `event_id`: повтор одного события не создаёт дубликат.

## 14. Безопасность

- Все внешние соединения работают только по HTTPS/TLS.
- `project_id` не является секретом и не даёт доступ.
- Init token одноразовый, действует 10 минут и привязан к проекту.
- Agent token ограничен одним агентом и одним проектом.
- Токены и пароли хранятся в БД только как хеши.
- Агент не получает доступ к PostgreSQL, панели администратора, Telegram token или токенам других проектов.
- Secrets не хранятся в skills, Git, YAML, логах или отчётах.
- Deep Agents работает непривилегированным пользователем.
- Работа ведётся в отдельном Git worktree на ветке `task/<task_id>`.
- Агент не получает Docker socket, домашний каталог, SSH-ключи или production-доступ по умолчанию.
- Публикация разрешается только после пользовательского решения `publish`.
- Докплой-интеграция должна использовать ограниченный webhook конкретного приложения, а не административный ключ Dokploy.

## 16. Развёртывание

### Центральный сервер

В Dokploy используются два Compose-стека:

1. `deploy/db/docker-compose.yml` — PostgreSQL с постоянным volume.
2. Корневой `docker-compose.yml` — `migrate`, `server`, `console`.

Требования:

- `migrate` выполняет миграции до запуска `server`;
- PostgreSQL не публикуется наружу;
- все сервисы подключены к `dokploy-network`;
- API, панель и MCP доступны через Dokploy/Traefik по HTTPS;
- Harness не входит в центральный Compose;
- секреты находятся только в Dokploy Environment;
- PostgreSQL сохраняет данные при пересборке сервера.

Минимальные переменные:

```text
DATABASE_URL
JWT_SECRET
ADMIN_EMAIL
ADMIN_PASSWORD
TELEGRAM_BOT_TOKEN
TELEGRAM_WEBHOOK_SECRET
TRANSCRIPTION_PROVIDER
TRANSCRIPTION_API_KEY
PUBLIC_BASE_URL
```

### Harness

Harness запускается на машине, где находится Git-проект.

Требования к машине:

- Git;
- Deep Agents;
- доступ по HTTPS к центральному серверу;
- доступ к разрешённым проектным инструментам, только если это необходимо назначенным skills.

## 17. Критерии приёмки MVP

MVP принят, если выполнены все условия:

1. Есть два независимых репозитория: сервер и Harness.
2. Сервер с панелью и PostgreSQL разворачивается в Dokploy.
3. В панели создаётся проект и агент.
4. В панели есть раздел Skills с категориями и карточками навыков.
5. Skills назначаются конкретному агенту.
6. `harness init <project_id>` подключает агент к проекту через одноразовый init-код.
7. После установки создаётся только `workflow/` с конфигурацией и назначенными skills.
8. Harness не содержит жёстко зашитой логики Git, Dokploy, деплоя или конкретного фреймворка.
9. Пользователь может отправить задачу голосом в Telegram.
10. Голос превращается в текстовую задачу и появляется в панели.
11. Агент получает задачу, использует skills и передаёт план.
12. Пользователь может неограниченно улучшать план перед запуском реализации.
13. До подтверждения плана агент не меняет код и не публикует проект.
14. После подтверждения агент реализует задачу, запускает проверки и отправляет отчёт.
15. Пользователь может принять работу, отправить на доработку или оставить результат без публикации.
16. Git push и Dokploy deploy запускаются только после явного принятия работы пользователем.
17. Агент передаёт ход работы и результат через REST API или MCP.
18. Панель показывает задачи, статусы, агента, план, прогресс, skills, тесты и итог публикации.
19. При ошибке или потере связи задача не теряет историю, отчёт или checkpoint.
20. Токены и секреты не попадают в Git, логи, skills, YAML или отчёты.
